Three more hours: does the gap between torch.compile and torch.vm widen?

The same two AI agents continue for a second three hours on one model, one improving torch.compile and one torch.vm. The best recorded throughput barely moves; what moves is how much of torch.compile's speed holds up when it is checked. Nov 20, 2026.

The first page gave two instances of the same AI coding agent three hours each to raise the throughput of TorchBench's yolov3 in inference, one through torch.compile and one through torch.vm, and plotted throughput against the time and tokens spent. It ended at 3,973 against 4,507 images/s, with a caveat on each number. This page is the same experiment continued: the same two agents, resumed where they had stopped, with the same rules and the same harness, for three more hours each. One thing was added, the same for both: each agent was told what the checks after the first half had found for its own side, was given a command that runs those checks on its current state, and was told that this page would report two numbers per side, the best recorded throughput and the best recorded throughput among states that pass every check.

In short. On the best recorded throughput the gap widened a little, from 13% to 16%: torch.vm went from 4,507 to 4,614 images/s with one step, and torch.compile recorded nothing above its 3,973. Both were already at the speed of the GPU's kernels, and neither agent built the next kernel it had named. On the throughput that passes every check the gap closed by more than half, from 71% to 27%: torch.compile went from 2,641 to 3,634, because its agent made freezing notice a weight update, which is the thing torch.vm had and it did not. On the way that agent found a bug in one of its own changes of the first half, which the checks on the first page had not caught: through the compile cache, a model could compute with the first convolution's weight of another model. And a probe added for this page, which neither agent was told about, goes against torch.vm: once the whole model is one graph it does not notice an edit of a module attribute that is not a tensor, which torch.compile with all its guards does. The second three hours cost more than the first ($42 and $49 of tokens, after $30 and $41) and bought less speed.

Does the gap widen?

  • On the best recorded number: slightly, and not because anything pulled away. torch.vm gained 2% in the first 40 minutes (the replay of the recorded kernels is now started before the call has been checked, step 1) and nothing after. torch.compile's best is still the first half's row; the same configuration measured again after the bug fix gives 3,861. A call is 1.73 ms for torch.vm, 1.70 of it on the GPU, and about 2.0 ms for torch.compile. What separates them is what separated them after three hours: torch.vm's convolutions run through the fused cuDNN kernel its agent wrote in the first half, and torch.compile's 3x3 convolutions still make a second pass over memory for the bias and the LeakyReLU. Each agent had named its next kernel-level step (that fusion for torch.compile; one kernel for a 1x1 convolution and the 3x3 behind it for torch.vm). Neither started it.
  • On what passes every check: it narrowed, from 71% to 27%. This is where torch.compile's three hours went. After the first half, its only states that followed a weight update were the first two. Its agent made freezing sound (step 2), then won back most of what the guards cost (steps 4 and 6): 3,634, which is 94% of its fastest configuration. What is left between the two lines is 0.11 ms of guards per call.
  • Told what the checks had found, both agents worked on what the checks had found. Most of the 16 rows recorded in the second half are repairs, not speed: torch.compile's freezing and its bug, torch.vm's speed after a change of image size, a module state that differed from eager's, and training, which is now one graph for torch.vm.
  • The slope flattened for both. The first three hours bought torch.vm 3,723 images/s and torch.compile 1,960; the second three bought 108 and, on the line that moved, 993. In tokens the second half was the more expensive one for both, because an agent that continues re-reads everything it has done so far at every step.

The bug, and what it means for the first page

The first page said that every recorded state of both sides predicted as well as eager on real weights. That was measured, and it was not the whole truth for torch.compile's states from its seventh step on. Those states were right as long as Inductor's compile cache had been filled by the same model. Compiled once for a model with other weights and the same shapes, they took the first convolution's weight from that other model (what happened, in the appendix). The checks on the first page compiled every state for the pretrained model only, so they could not see it; the agent saw it in the second half because it ran the pretrained-weights check on configurations it had first compiled for the benchmark's random weights.

The check below does that on purpose: with an empty cache, a state is compiled for the benchmark's random-weight model first and for the pretrained model second.

What this does and does not show

  • One model, one run per side, and now one continuation. It is still an example. A different second half is easy to imagine: had either agent started on its next kernel, the best recorded numbers would have moved instead.
  • The second half was not a blind continuation. Each agent was told what the checks had found for its side and that the checked number would be reported. That is why both spent their time on soundness; an agent told only to raise the throughput might not have.
  • "Passing every check" is as strong as the checks. They did not catch the cache bug until an agent tripped over it, and one probe added afterwards was enough to find something neither side's fast states follow, and that torch.vm has no guard for at all. A state that passes them is not thereby proven equal to eager, and the comparison of the two "checked" lines is only fair for the checks both agents knew.
  • Agents write bugs into compilers. Both sides shipped one in the first half that the tests and the checks let through: a stale weight through the cache on one side, module attributes left at another image size's values on the other. Both were found by the agent that wrote them, in the second half, once it had a stronger check or a reason to look.
  • Not on the x axis, as before: the tokens that built torch.vm up to the start, and those of the session that set this up and checked it.

How the second half was run

  • The two agents of the first half were resumed with their whole history, about three hours after they had stopped; the pause is not counted as their time. The trees and configurations were their final states, measured again before the start (3,860 and 4,506 images/s).
  • Rules, harness and measurement as before. Added, in the same words for both: the list of checks, that they would be run again, that both numbers would be reported, a command to run the checks, and that neither side reads the other's directory or the first page.
  • Each agent got the findings for its own side only: for torch.compile, which states followed what, the error at a recompilation, the cuDNN error in one run; for torch.vm, that every state passed, that the speed did not come back after events, and that training ran a graph per layer.
  • torch.vm's agent stopped once with 23 minutes left and was told to go on, as both had been in the first half.
  • Tokens at list price, as before: $72 for torch.compile's agent over the six hours (492k output tokens, 190 million cached input tokens read) and $90 for torch.vm's (597k and 184 million).

Appendix: every step of the second half, in detail

In the order of the tables above. The figures inside a step are from the agent's own profiles, as its journal has them; the images/s in a heading are the recorded measurements. The steps of the first three hours, and the terms used here (host time, CUDA graph, weights built in, guards), are explained in the appendix of the first page.

torch.compile

1. The state that already passed everything, recorded 2,784 images/s

The checks after the first half had found one torch.compile state faster than its start that passed all of them: the agent's final source with CUDA graphs and nothing else, no freezing and no guard filter. The agent recorded it first, as the floor of its second line.

2. Freezing that notices a weight update 2,784 → 3,404 images/s

The problem. Freezing builds the weights into the graph, and after that nothing looked at them again: every frozen state of the first half kept computing with the old values after a weight was updated in place.

Change, in five files of Dynamo and Inductor. Every tensor in PyTorch carries a version counter that goes up on each in-place write (autograd uses it to notice that a tensor it saved was modified). Freezing now records which tensors it built into the graph, and Dynamo guards the version counter of exactly those. When one of them has been written to, the guard fails, the function is compiled again and the new values are built in. Tensors the graph writes itself (a batch norm's running statistics in training mode) are not frozen and get no such guard, so a training-mode call does not recompile every time.

Cost. One recompilation per weight update, about 9 s here; the configuration raises Dynamo's limit on recompilations from 8 to 32, since the ninth would otherwise send the function back to eager for good. And 370 more guards to check on every call (step 4).

What it still misses. A write through tensor.data does not move the version counter and is not followed.

The first row recorded with this change (3,413) is struck, because of the bug in the next entry; 3,404 is the same configuration on the corrected source.

3. A bug in a first-half change: a weight that came from another model

How it showed. With the pretrained-weights check now at hand, the agent ran it on a new candidate and got a wrong result outright: 2.88 from eager where a correct state is at 0.05, with the first convolutions' outputs off by half their size. On the benchmark's random weights the same candidate had looked right to the last bit. For most of an hour it looked like a matter of settings ("it takes all four of these together"), because whether a configuration was right depended on something else: which model had been compiled with it first.

The cause was the agent's own step 7 of the first half, the fourth input channel for the first convolution. For a frozen weight that change computed the padded weight while compiling and registered it as a new constant of the graph. Inductor keeps compiled graphs in a cache on disk. For a frozen graph, the cache's key covers the shapes and types of the frozen weights but not their values, since those are supplied again from the model on a cache hit; constants that are created later, while the graph is turned into kernels, are stored in the cache entry as they are. So when the same architecture was compiled a second time with other weights, the cache handed back the first model's padded weight for the first convolution, and everything else from the second.

The fix. The weight is padded when the code runs (one small kernel per call) and no constant is created.

What it means for the rows. The first-half rows from that step on, and the 3,126 row of this half, were measured with a cache that the same model had filled, so their numbers are for the right function; but those states would have computed with a stale weight after another set of weights had been compiled. The 3,413 row was measured in exactly that situation (error against float64 4.97 times eager's, inside the harness's limit of 10) and is struck. The check that reproduces this is in the section on checks above.

4. A narrower guard filter 3,404 → 3,549 images/s

What the guards cost now. With every guard and the 370 version guards, the check before each call takes 197 microseconds; the first half's unsafe filter, which drops every guard on a module, takes 3.

Change. A filter of the agent's own that keeps the guards on tensors (their identity and, new, their version) and on each module's training flag, and drops the guards on the modules' other attributes: 114 microseconds, nearly all of it the version guards.

What it gives up. An edit of an attribute of a module that is not a tensor, after compilation (a stride, a slope, a hook), is not noticed. The probes of the first half had no such edit; one was added for this page, and the table of probes above has the outcome.

5. The fastest configuration again, on the corrected source 3,861 images/s

The configuration of the first half's best row (3,973: freezing, every guard on a module dropped, CUDA graphs without trees), measured on the source without the bug. It follows neither weight updates nor a replaced parameter nor model.train(), as before. The 3% to the earlier number is the small kernel that now pads the weight on every call, and the spread between processes these rows have.

6. CUDA graphs without trees, and static shapes 3,549 → 3,634 images/s

A slowdown the checks had not looked for. After the whole sequence of probes the same callable ran at about 1,480 images/s instead of 3,560. The agent timed it step by step: the speed held through the weight updates and the other shapes and fell when the last bias was replaced. By then the function had seen three input shapes, and Dynamo's automatic dynamic shapes compile the next version with symbolic sizes; that version ran without a CUDA graph. torch._dynamo.config.automatic_dynamic_shapes = False gives every shape a graph of its own with fixed sizes: the callable stays at 3,600 to 3,650 through the whole sequence, and a recompilation takes 9 to 20 s instead of up to 130.

Without trees. As in the first half, the older CUDA-graph path saves about 40 microseconds of bookkeeping per call, and gives up the error that the tree manager raises when a result is read after a later call has overwritten it. It also sidesteps an error the tree manager raises for this model (re-recording a graph after other shapes have run: "storage data ptrs are not allocated in pool"), which the agent reproduced without freezing and did not fix.

3,619, and 3,634 for the final state, which is the same source and configuration measured again.

7. One guard for all version counters 3,626 images/s, no gain

The 370 version guards are 106 of the narrow filter's 114 microseconds; reading the same 370 counters in one Python call takes 20. The agent replaced the 370 guards by one that checks all the counters. It measured the same: the loop over 370 weak references costs what the guards did. Reverted; the agent's note for later is one call in C over the frozen tensors, which would recover most of the 0.11 ms that separates 3,634 from 3,861.

torch.vm

1. The kernels started before the call is checked 4,507 → 4,608 images/s

What was left. At the start of a call the GPU sat idle for about 60 microseconds, 41 of them the runtime's look over the model's 370 tensors that tells whether this call is like the last one.

Change. If the input is in memory that one of the recordings reads in place, the recording that served the previous call is started as soon as the region is called, and the look is done while the GPU already runs. The results are handed out only if the look then confirms that the call was for that recording; otherwise they are dropped and the call is handled the ordinary way, which is safe because a recording writes only to memory of its own. A call goes from 1.766 to 1.727 ms. This is the only step of the second half that raised torch.vm's throughput.

2. The speed after another image size 4,599 and 4,614 images/s, unchanged

The finding it started from. The checks after the first half timed the final state again after a batch of another size, images of another size and a weight update: 4,533, 4,387, 4,205, 4,194 images/s. The speed did not come back.

First cause. To see where a graph's inputs lie in memory, the CUDA-graph code asked each for a pointer one can write through. For a watched tensor that request counts as a write, so weights that happened to be inputs of some graph lost their watch, and the graph for the timed shape was built again with 24 convolution weights as inputs instead of built in: their batch norms were folded on every call, 7% of it. The code now asks for the address without the right to write.

Second cause. For a new image size a YOLO layer stores two integers, self.nx, self.ny = ng. A region allowed stores of tensors (step 1 of the first half) but not of plain values, so for the new size the VM ran the model instruction by instruction once, with a graph per layer. A region may now store a plain value (a number, a string, None) into a module attribute, after its graph; what those attributes held before the call is part of what a compiled variant is keyed on, so a variant is only used for the state it was traced from. An attribute that is overwritten with a new value on every call, a counter, is still refused.

A wrong state this also fixed. Coming back to the first image size had left nx and ny at the other size's values, which eager does not do. The outputs were right, so none of the checks had seen it.

3. Training as one graph 4,602 images/s, unchanged

The first page noted that torch.vm was no faster than eager in training on this model. What kept the training-mode forward from being one region was one statement: in training mode the YOLO layer sets self.grid = None on every call, a store of None into a buffer that already holds None. With that allowed the training forward is one region of 709 operations. The measurements of training are in the section on checks.

4. Tried and dropped, and the rows without a change

Results as copy-on-write clones. Each call copies its results out of the recording (about 30 microseconds). Handing them out as lazy clones would copy only when someone writes, but on this build a lazy clone of a tensor on the GPU copies at once, so nothing was saved.

Building a changed weight in again after a quiet spell. After a weight update the new graph has that weight as an input. The agent tried building it in again once it had not changed for 64 calls: the speed after a weight update got worse, not better (4,479 against 4,535), and each time uses one of the eight graphs a function may have with weights built in. Reverted; the 4,611 row is that state and 4,606 the state put back.

Hardening. The agent's own tests of its changes grew from 16 to 22, among them three threads calling the same compiled function, and it ran random sequences of image sizes, batch sizes, train(), eval() and weight updates against eager, checking as well that no result a caller kept was changed by a later call.

Where a call's time is at the end. 1.73 ms, of which about 1.70 is the GPU's; 91 to 93% of that is the fused cuDNN kernels.
