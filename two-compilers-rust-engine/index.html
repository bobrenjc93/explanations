One model, two compilers, run again: torch.vm with its graphs built in the Rust engine

The experiment of the two earlier pages, repeated from the start after torch.vm's graph compiler was rewritten: two new instances of the same AI agent, six hours each, one improving torch.compile and one torch.vm on one model. Throughput against the time and tokens spent, every recorded state checked on real weights, and two numbers per side: the best recorded, and the best that passes every check. Nov 21, 2026.

The first page gave two instances of the same AI coding agent three hours each to raise the throughput of TorchBench's yolov3 in inference, one through torch.compile and one through torch.vm, a prototype compiler for PyTorch whose engine is written in Rust, and plotted throughput against the time and tokens spent. The second gave the same two agents three more hours. This page is a second run of the whole experiment: the same model, harness and rules, six hours in one go, two fresh agents that had seen nothing of the first run, and a torch.vm whose graph compiler had been rewritten in between. As before, each agent could change its compiler's options and its source; the model and the measurement were not theirs to touch, every gain was recorded by a harness neither could change, and every recorded state was checked again after the deadline.

In short. The two compilers now start close together: torch.compile at 1,954 images/s and torch.vm at 1,825 (eager does 802; in the first run it was 2,013 against 784). torch.compile moved first, by switching CUDA graphs on (2,591 after 7 minutes). torch.vm's agent had to build them, was ahead after 32 minutes (2,869) and was at 3,218 after 78, when torch.compile had 2,964. After that neither line moved much. The page reports two numbers per side. Best recorded: torch.compile 3,551, torch.vm 3,384. Best recorded among states that pass every check: torch.vm 3,218, torch.compile 3,015. So the expectation these charts were first drawn for, a higher start for torch.compile and a steeper slope for torch.vm, holds in this run only in a weak form: the start is 7% higher, the slope is steeper for the first 80 minutes, and the lead it buys is 7% on the checked line and is reversed on the other.

Three things qualify the end points. Six torch.compile rows are struck, its two highest among them (3,612 and, of the checked ones, 3,048): its agent introduced a test failure, found it itself after about 3 hours 45 minutes and fixed it, and the rule was that a state whose source breaks its side's tests does not count. torch.vm's 3,218 was measured once; the same configuration gave 3,145 to 3,162 in nine later rows, and its agent did not find out why. And the two best-recorded states give up different amounts. torch.compile's misses nine of the thirteen probes: it follows no in-place weight update except one, no replaced parameter, no model.train() and no edited module attribute, and a result kept across calls is overwritten. torch.vm's misses two: a weight written through .data, and a result held by its raw address across later calls, which is the hole its agent had reported. Neither agent wrote a convolution kernel of its own, which is what carried torch.vm past 4,500 in the first run; both ended at the speed of the kernels that Inductor and cuDNN provide.

What changed since the first run

In the first run, torch.vm's graph compiler was Python code. It took a stretch of tensor code that the VM had run, traced it a second time on fake tensors (tensors that have a shape and a type but no data), and handed the graph it got to AOTAutograd and Inductor, the backend torch.compile uses. Whatever the trace read on its way, a flag or an attribute of a module, was fixed into the graph, and a separate check of the modules decided whether a later call could use it.

Now graphs are built inside the Rust engine, from the path a call actually took on real tensors: its instructions in the order that call ran them, through the branches as they went and round the loops as often as they went round. Every value Python read on the way is read again and compared on every call. AOTAutograd and Inductor are no longer the compiler but optional passes over the graph the engine exports; without them the engine runs the graph's kernels itself and the results are eager's bit for bit. The stack is described in its top pull request, pytorch/pytorch#204763.

Two consequences are on this page before either agent did anything. torch.vm starts at 1,825 images/s where it started at 784: the model is one graph of 328 operations out of the box, where the first run began with a refused store into a module's buffer and the model running kernel by kernel. And an edit of a module attribute that is not a tensor (the slope of a LeakyReLU), which every one-graph torch.vm state of the first run missed, is followed by every torch.vm state of this run: the slope is one of the values that are read again on each call.

Also different in this run:

  • Six hours in one go, not two halves, with fresh agents. They were told not to read the first run's directory or anything published about it.
  • The checks were announced from the start, with a command that runs them on an agent's current state, and both agents knew that the report would give two numbers per side. In the first run the checks came after the first three hours.
  • Each side worked on its own copy of the source tree, with eight CPU cores of its own.
  • Other work ran on other cores of the same machine during the run. It used no GPU.

What the charts show

  • The start. torch.compile is 7% ahead (1,954 against 1,825), where it was 2.6 times ahead. Both now begin with the whole model as one compiled graph, and both agents' first profiles say the same thing in almost the same numbers: about 4 ms of CPU time per call to launch 330 kernels that need 2.5 ms of the GPU.
  • The first step is the same step. Both went to CUDA graphs. For torch.compile that is an option, recorded after 7 minutes. torch.vm had none, and its agent wrote one in 24 minutes (2,405). What put torch.vm ahead eight minutes later is specific to it: its checks of a call cost more than torch.compile's guards (0.54 ms against 0.2), and instead of thinning them out its agent started the GPU's work before them, so that they run while the kernels do.
  • The slope. On states that pass every check, torch.vm gained 1,393 images/s in its first 78 minutes and $17, and nothing after. torch.compile gained 1,010 in its first 71 minutes and $13, and 51 more by the end. From 32 minutes on torch.vm is ahead on that line at every time and every budget, by 7% at the end; measured against the level its configuration held later (about 3,150), by 4.5%.
  • The best recorded line is the other way round. Both agents kept a second, faster configuration that gives up things eager does, and said so in each row's note. torch.compile's reached 3,327 after 86 minutes and 3,551 at the end; torch.vm's reached 3,338 after 117 and 3,384. torch.compile ends 5% higher, and gives up far more for it (below).
  • Both lines are flat after an hour and a half. The steps after that are a few percent each and many are inside the noise. Both agents were then bound by the same kernels: cuDNN's convolutions (1.5 ms per call) and the generated batch-norm-and-LeakyReLU kernel behind each of them (0.5 to 0.6 ms). In the first run torch.vm's agent replaced that pair with one cuDNN kernel through an interface PyTorch does not expose; its line stood at 3,261 before that kernel and ended at 4,614. In this run torch.compile's agent named that fusion as what would help and did not build it, and torch.vm's tried a generated kernel for the first convolution, found it four times slower and stopped there. The steep second half of the first run was one agent's kernel, not a property of the compiler it was written for.
  • Per token. torch.compile's agent spent more: $65 against $54, with about the same output (464k and 444k tokens) and more re-reading of its own history (195 against 144 million cached input tokens, over 413 against 286 responses). At equal dollars the picture is the one at equal minutes.

Which states pass every check

The rules both agents had named the checks and added: "Other things eager does that are not listed here. A state that is found not to do one of them does not pass." On this page a state passes every check when

  • the harness counted its measurement (outputs equal to eager's on the benchmark's inputs, its three probes);
  • its predictions with the pretrained weights are eager's (mAP@0.5 within 0.01);
  • it follows all ten announced probes and the three that were not announced;
  • its source passes its side's tests. A row whose source fails one that the starting source passes is struck, as the rules said it would be.

Two more checks were run on four states only, each side's highest row and its last: the compile cache filled by a model with other weights, and the speed after events. They are reported below; none of the four fails the first. By this count 7 of torch.compile's 17 rows pass and 14 of torch.vm's 21.

What the states follow

With the pretrained weights, after the callable is warm, one thing is done to the callable's model and to an eager copy, and the two outputs are compared; then it is undone and they are compared again. For the last two probes the caller keeps every tensor of one call's result and looks at them again after two calls with other inputs. The table has one column for each group of states that came out alike.

The three probes that were not announced are a second version. In the first, the two probes of kept results held only the first tensor of a result, and their last call repeated the input of the call whose result was kept, so memory that had been overwritten compared equal again. Both were too weak and were replaced before this page was written; the first version's script and outputs are kept with the results and are not used here.

What torch.compile's unchecked variants give up. Nine of the thirteen probes, the same nine on all 6 states. Their weights and batch-norm statistics are constants of the graph, so an in-place update of a convolution's weight, a batch norm's bias or a running mean is not followed; the one weight update that is followed is the last convolution's bias, which nothing is folded into. Their guards cover only the call's arguments (in the first variant, only tensors), so a replaced parameter, model.train() and the edited slope go unnoticed, and after model.train() and model.eval() the callable stays wrong. A write through .data is not followed either. And their results are handed out in memory that later calls write again: kept across two calls with other inputs, as tensors or through DLPack, all four tensors of a result hold other values afterwards. The agent's own notes on these rows say all of this except the .data write, which follows from the first item.

What torch.vm's fast configuration gives up. Two of the thirteen probes on the six states that hand large results out without a copy (rows 7, 8, 11, 13, 15 and 17), and one on the state that only keeps the weight layouts (row 5). On all seven, a 3x3 convolution's weight written through .data is not followed, because the kept channels-last copy of the weight is refreshed only when the weight's version counter moves. On the six, a result held by its raw address, through a DLPack capsule, is changed by later calls: two of the four tensors of a result, by their sizes the two raw head outputs above the option's threshold of 1 MB, which are handed out on the recording's memory. That is the hole its agent reported for these states. Held as tensors, the same results stay what they were: before the recording runs again, a handed-out tensor that somebody still holds is given memory of its own. Everything else is followed, including the in-place updates and the attribute edit.

The checked and the safe lines follow all thirteen. What their agents say they still give up is in the section on what the agents found.

What this does and does not show

  • One model, one run per side. An example of two paths, not a measurement of two slopes. Run again, either agent might have written a kernel, or missed a step it found here, and the end points would differ by more than the gaps on this page.

How it was run

  • Model and setup as the PyTorch performance dashboard has them: eval mode, batches of 8 images of 3x384x512, bfloat16, no_grad, one H100.   • The checks on this page were made after the deadline by the session that set the experiment up, on the snapshot of every row the harness had counted: predictions, the ten announced probes, three that were not announced, and each side's tests; the compile-cache check and the speed after events on each side's highest and last row; training on the starting and final sources. Appendix: every step, in detail

What each agent found, what it changed, why that is faster, what it measured and what it gives up, in the order of the tables above. The figures inside a step (microseconds per kernel, milliseconds per call, the ratios of an A/B comparison in one process) are the agent's own, from its journal and its final summary; they were not measured again for this page. The images/s in a heading are the recorded measurements before and after, each the median of three processes. What a state follows and whether its tests pass is from the checks made afterwards, not from the agents' notes.

The model, for orientation. One call is a batch of 8 images through 76 convolutions. 73 of them are followed by a batch norm and a LeakyReLU, 23 results are added to an earlier one (the residual connections), one tensor goes through three max pools with windows of 5, 9 and 13, and three detection heads turn their convolution's output into boxes with a few sigmoids and exponentials; their three results are concatenated. Compiled, that is about 330 GPU kernels in this version of PyTorch: the convolutions are cuDNN's, everything between them is kernels that Inductor generates, and together they take about 2.5 ms.

Terms that come back.

  • Host time. Each kernel is launched from the CPU, through Python, PyTorch and the driver, at 10 microseconds or more apiece. For 330 small kernels that is more than the GPU needs to run them, so the GPU waits for the CPU.
  • CUDA graph. A recording of all the kernel launches of one call. Replaying it starts them with one call into the driver. The recording is tied to the memory the recorded call used: it reads its inputs and writes its results at fixed addresses. So each call's input is copied to where the recording reads it, the results sit in memory that the next replay writes again, and each new input shape needs a recording of its own.
  • Guards, and the checks of a call. Compiled code is right only for the situation it was compiled in: these modules, in this mode, holding tensors of these shapes. Before it runs the compiled code, torch.compile evaluates guards, one small check per assumption (about 3,700 for this model). torch.vm does the equivalent by going through the instructions of the path again without the tensor operations, re-reading every value Python read and comparing it (13,604 instructions for this model).
  • Weights built in. A compiler can treat the model's weights as inputs of the graph or as constants of it. As constants they can be combined ahead of time (a batch norm folds into its convolution) and stored in the layout cuDNN prefers. The price is that the graph is right only while the weights hold what they held.
  • Channels last. cuDNN's fast half-precision convolutions want images and weights stored with the channel as the last dimension. PyTorch stores them with the channel second. With the weights as inputs, the compiled code copies each 3x3 weight into the other layout on every call (a 1x1 weight is the same bytes in both).

torch.compile

Start: the dashboard's configuration 1,954 images/s

torch.compile of a function that calls the model, with the Inductor backend in its default mode. The agent's first profile: a call takes 3.92 ms, and for 3.78 ms of it the CPU is launching about 330 kernels from Python; the kernels themselves need about 2.6 ms of the GPU (cuDNN's convolutions 1.54 ms, the kernels between them about 0.8, the copies of the weights into channels last about 0.15, the detection heads 0.13). The host is the bottleneck, not the GPU.

1. CUDA graphs, with the results copied out 1,954 → 2,591 images/s, 7 minutes in

Change. One option, mode="reduce-overhead", later written as options={"triton.cudagraphs": True}: Inductor records the compiled graph's kernels as a CUDA graph and replays it. And a few lines in the configuration that clone every tensor the compiled function returns.

Why it helps. The 330 launches become one replay.

Why the clones. The results of a replay lie in the recording's memory, and the next call writes them again. Eager hands out new tensors on every call, and a caller may keep them. The agent decided at the start that its main line would hand out copies; it later measured their cost at 0.9% (3,020 against 3,046 images/s in one process).

What it gives up. Nothing that the checks look at. One thing it inherits from the start: after an input of another shape, the dashboard's configuration recompiles with symbolic sizes and the new graph then also serves the timed shape, more slowly. The agent ran the speed-after-events script on the starting configuration and on this one, one process each: 2,066 → 1,845 → 1,189 and 2,600 → 1,936 → 1,245 images/s. Step 3 removes that.

2. The heads' concatenation unfused, and a cheaper guard check 2,591 → 2,757 images/s, 36 minutes in

The concatenation. The model's result is the torch.cat of the three heads' outputs. Inductor had fused it with the arithmetic of its inputs into one kernel, in which every element of the result evaluates the expressions of all three heads and then picks one: 0.134 ms. "max_complex_pointwise_cat_inputs": 0 makes each head write its own slice of the result: 0.04 ms. In one process on the final tree the option is worth 2.7% (2,907 against 2,985).

The guards. Of the 0.46 ms the CPU still spent per call, about 0.2 was Dynamo's guards. torch._dynamo.config.use_recursive_dict_tags_for_guards = True lets Dynamo skip all guards under a module when neither its attribute dictionary nor those of its submodules have been modified since the last check, which Python can tell from a version tag on each dictionary: 202 to 130 microseconds.

What it gives up, by the agent's own later finding: assigning a new __class__ to a module nested inside such a module does not touch any dictionary, and is not noticed. The agent reproduced that on the unmodified tree with this flag, on a small model on the CPU; without the flag it is noticed. The checks made for this page have no such probe.

About this row. Its third process ran while the agent was already editing a source file for the next step, and recompiled (2,806). The two clean processes gave 2,757 and 2,754, and the median is one of them. From here on the agent developed in a copy of its tree.

3. Max pool one dimension at a time; module guards on the fast path; hooks followed; a graph per shape 2,757 → 2,964 images/s, 71 minutes in

Four things in one row; only their sum was measured officially.

Max pool, in Inductor (torch/_inductor/lowering.py). The three max pools took 0.124 ms. Inductor computes each output as the maximum over the whole window, so the 13-wide pool reads 169 values per output element. The maximum over a rectangle is the maximum over its rows of the maximum along each row, so when only the pooled values are used (not the positions of the maxima) the pool can run as one pass per dimension: 13 + 13 reads. The lowering does that where it at least halves the reads. A maximum involves no rounding, so the result is the same bits.

Module guards, in Dynamo (torch/_dynamo/guards.py). The model's loop over its 114 layers reads module.__class__.__name__ to decide what to do with each. The guards on that read kept every one of those modules off the fast path of step 2. The change counts module.__class__ and cls.__name__ as safe for that path, under an existing setting that says such attributes are assumed not to change. In a test on the CPU the guard check went from 120 to 78 microseconds; the agent did not isolate its share of this row.

Hooks. torch.compile by default does not notice a forward hook that is registered on a module after compilation. The agent set skip_nnmodule_hook_guards = False, so that it does, as eager does. Cost: 1.4% (2,999 against 3,043 in one process), and only that little because of step 2: with the hook guards on, switching the dictionary tags off takes the callable from 2,999 to 2,686 images/s.

A graph per shape. Run on its own state, the speed-after-events script gave 2,954 images/s at first, 2,121 after a batch of 3 and 1,380 after another image size. With dynamic=False every input shape gets a graph of its own with fixed sizes: 2,877, 2,943, 2,941, 2,952. This adds nothing at the timed shape; it keeps the speed afterwards.

4. The pool passes as unrolled kernels 2,964 → 2,992 images/s, 96 minutes in

The 9- and 13-wide one-dimensional passes of step 3 had been generated as reduction kernels, a loop with a running maximum per output element: 16 microseconds each. A kernel that reads the 9 or 13 values and takes their maximum in one expression is faster. Inductor already does that for windows below a threshold; inside the new path the threshold is raised to 25. The three pools now take 0.014 ms, from 0.124 at the start. dynamic=False was replaced by torch._dynamo.config.automatic_dynamic_shapes = False, which has the same effect without patching a setting on every call (about 11 microseconds).

The recorded step, 0.9%, is inside the noise. This is the highest row of the line that passes every check until the fix of step 8.

5. A fourth input channel for the first convolution, and the regression in it 2,992 → 2,966 images/s, 133 minutes in; struck

What was measured. The first convolution reads images with 3 channels, and cuDNN's half-precision channels-last kernel is slow for exactly that: 0.1015 ms, against 0.0786 with the input padded to 4 channels (8 channels: no better).

Change, in Inductor's convolution lowering (torch/_inductor/kernel/conv.py): a half-precision channels-last convolution on CUDA with 3 input channels gets a channel of zeros appended to its input and zero weights for it. A zero times a zero adds nothing to any sum; what changes is which kernel cuDNN picks. In the full graph the first convolution went from 0.101 to 0.076 ms. The recorded row did not move: 2,966 after 2,992, which the agent put down to noise between sessions.

The regression. As first written, the change padded every such convolution, also one whose input and weight are already stored channels last. There it adds padding kernels where none are needed. PyTorch has a test for exactly that case, test_require_stride_expanded, which asserts that such a convolution generates no kernel, and whose half-precision run now failed. Before this measurement the agent had run the Inductor GPU tests whose names contain conv (352 pass); the name of this test does not. It found the failure about 3 hours 45 minutes in, when it ran the whole suite. By then six rows had been recorded on sources that contain it. They are struck (the table above); step 8 is the fix.

6. Filter counts rounded up to a multiple of 8 2,966 → 3,046 images/s, 152 minutes in; struck

What was measured. The three detection-head convolutions have 255 output channels. cuDNN's fast channels-last half-precision kernels want a multiple of 8 and otherwise fall back to much slower ones: 55, 30 and 22 microseconds for the three heads, against 9, 5 and 4 with 256 filters.

Change, in the same lowering: for a half-precision convolution with 64 filters or more whose count is not a multiple of 8, the weight is padded with all-zero filters up to the next multiple, and the extra output channels are sliced off. The channels that are kept are computed from the same numbers as before.

Effect. +2.7%, the last step of this line that is clearly outside the noise. The row is struck because its source still has the regression of step 5; the change itself is in the final source, where the same graph measures 3,014 and 3,015.

7. One input copied with copy_ 3,046 → 3,048 images/s, 162 minutes in; struck

Inductor's CUDA-graph code copies each call's inputs into the recording's memory with one batched kernel for all of them. For a single input the agent replaced it by a plain copy_, which goes through the device's memcpy (torch/_inductor/cudagraph_trees.py). No measurable gain; the agent's summary lists it as an estimate that was never confirmed.

8. The fix: the input is padded only where it is copied anyway 3,014 and 3,015 images/s, 248 and 277 minutes in

Change. The zero channel of step 5 is now added only when the convolution's input has to be copied into channels last anyway. The copy then writes the padded input instead, so no kernel is added, and a convolution whose input is already channels last is left alone. test_require_stride_expanded passes again. For yolov3 the graph is the same as before the fix: 127 generated kernels, the first convolution at 0.0765 ms.

The two rows. 3,014 is the corrected source with the checked configuration. Because it read lower than the struck 3,048 of the same graph, the agent measured the unchanged state once more: 3,015. Its journal says, before the second result was in, that the decision to measure again depended on the first result, so the two are two samples of one state and not a best of two. It also measured two processes of identical code 2% apart in GPU time, which is the size of the difference to the struck rows.

The unchecked line: weights built in, guards dropped, results not copied 3,327 → 3,405 → 3,551 images/s; 3,524, 3,570 and 3,612 struck

From 86 minutes on the agent kept a second configuration next to the first, for the report's first number, and switched its config.py back after each measurement. Every one of these rows says in its note what it gives up.

Variant 1 (3,327). freezing builds the weights into the graph: the batch norms fold into their convolutions and the weights are stored channels last once. By itself it was slower (2,371): Dynamo passes a model's parameters to the graph as inputs, so nothing was folded, and the CUDA-graph code copied all 375 inputs on every call. With torch._dynamo.config.install_free_tensors = True the parameters become constants of the graph and freezing works. Variant 2 (3,405; again on a later source: 3,524, struck). A guard filter of the agent's own that keeps only the guards on the call's arguments and on global state. Variant 3 (3,570, struck). "triton.cudagraph_trees": False selects Inductor's older CUDA-graph path, without the bookkeeping that tracks which results are still alive and where the weights lie: +1.4% in one process.

Variant 4 (3,612, struck; on the corrected source 3,551). "max_pointwise_cat_inputs": 0 makes every concatenation a kernel of its own: +1.4% in the frozen graph (in the checked configuration the same option is 1.8% slower).

What these states give up, as the probes found it (all six states alike; the table above). Not followed: an in-place update of a convolution's weight, of a batch norm's bias or of its running mean; a parameter replaced by a new one; model.train(), and after model.eval() the callable is still wrong (the agent's reading: eager's training-mode call moved the batch norms' statistics and the frozen graph has the old ones); the edited slope of a LeakyReLU; a weight written through .data; and all four tensors of a result that the caller kept, as tensors or through DLPack, hold other values two calls later. Followed: an update of the last convolution's bias, which is folded into nothing, so the graph still reads the tensor itself (it is why the harness's own weight probe passes on these rows), other batch and image sizes, and the timed shape again. Their predictions on the pretrained weights are as good as eager's.

What did not help, and where a call's time is at the end

Where a call's time is at the end, checked configuration: the replay is 2.31 ms of GPU work and a call takes 2.73 ms. Of the rest, about 0.3 ms is CPU work in front of the launch: the guards (about 0.1 ms), handing 374 parameters to the graph, the check that they still lie where the recording reads them, and wrappers. Without waiting for the GPU between calls the same callable runs 3,451 images/s. After a model.train() and model.eval() round trip it is about 10% slower for the rest of the process (3,010 images/s before, 2,713 after): the toggle switches the dictionary-tag fast path of step 2 off, so every guard runs in full. torch.vm

Start: the dashboard's configuration 1,825 images/s

The default passes, Graphs() and Inductor(). The engine takes down the path a call takes through the model as one graph of 328 tensor operations and hands it to Inductor. The agent's first profile: launching that graph's kernels keeps the CPU busy for 4.10 ms per call while the GPU works for only 2.53 ms (cuDNN's convolutions 1.55 ms, the generated kernels 0.97). Of the CPU's time, 0.54 ms is the engine in front of the graph, going through the path's 13,604 instructions to re-read and check what the path depends on, and 0.13 ms is the engine behind it.

1. A CUDA graph around what Inductor compiled, built as a new option 1,825 → 2,405 images/s, 24 minutes in

The problem is torch.compile's: 4.1 ms of launching for 2.5 ms of kernels. torch.compile has an option for it; this version of torch.vm had none, so the agent wrote one: Inductor(cuda_graphs=True), in a new file torch/vm/_cudagraphs.py.

How it works. The first call runs the compiled function as it is, which loads the kernels, lets cuDNN choose its algorithms and shows whether the function writes to what it is given. The second call is recorded as a CUDA graph. A tensor that lay at the same address in both calls (a weight) is read where it lies, and every later call checks that it still lies there; what it holds is read when the kernels run, so a weight updated in place is followed. The other tensors (the input) are copied into memory of the recording, and the results are copied out, so a caller gets tensors of its own. When a tensor that was read in place is found somewhere else (a parameter that was replaced), the graph is recorded again and reads it where it now lies; a tensor that moves a second time is copied from then on.

When it does not apply. Calls that record gradients, graphs that write to their inputs, that compute a tensor on the CPU from anything but numbers, or that hand back one of their inputs run the compiled function as before.

Effect. The CPU's launch work fell from 4.10 to 1.47 ms per call. A call now took 3.3 ms against 2.74 ms of GPU work: what remained was the engine's walk in front of the graph. Nothing is given up: the state passes every check.

2. The graph started ahead of the engine's checks 2,405 → 2,869 images/s, 32 minutes in

The problem. Before the graph could start, the engine went through the path: 0.54 ms on the CPU with the GPU idle, and 0.13 ms more behind the graph. That walk is what makes torch.vm notice an edited attribute or a module switched to training mode, so it cannot be dropped the way a guard filter drops guards.

Change, in the Rust engine and in the new file. When a function is called, the engine first asks the graph that served the previous call to start, with the arguments it already has in hand. That graph checks that the tensors it reads in place are still where they were, copies the input in and launches the replay. Only then does the engine walk the path, while the GPU works. If the walk confirms that this call is one the graph was made for, the results are copied out. If not, the run is discarded and the call is handled the ordinary way.

Why that is safe. Until its results are handed out, a replay has written to nothing but the recording's own memory, so a run that is thrown away leaves nothing behind. The tensors it reads in place are kept alive for as long as it may read them. A graph that draws random numbers is not started ahead, because the numbers of a discarded run would be missing from the generator. After a start that was for nothing, the graph waits longer before it is started ahead again (twice as many calls each time, up to 32).

Effect. A call takes 2.79 ms against 2.70 ms of GPU work: the callable is bound by the GPU from here on. This is torch.vm's largest step after CUDA graphs, and it has no counterpart on the other side, where the 0.1 ms of guards still runs in front of the launch at the end.

3. A pass: max pools as two one-dimensional pools 2,869 → 2,971 images/s, 45 minutes in

The agent's profile of one replay, in microseconds: convolutions 1,526, batch norm and LeakyReLU kernels 522, max pools 123, weight copies into channels last 121, the heads about 150, copies of input and results 62.

Change. A new pass over the graph the engine exports, torch.vm.passes.SplitPools(), which the configuration puts between Graphs() and Inductor(): a max pool over a window of 16 elements or more becomes two pools, one along each dimension of the window. It is the rewrite torch.compile's agent put into Inductor's lowering (its step 3), done here on the graph before Inductor sees it, and exact for the same reason. The three pools went from 123 to 14.5 microseconds.

4. Values that a compiled graph keeps for itself 2,971 → 3,218 images/s, 78 minutes in

What the agent found. It listed what the engine still runs after the graph. Each detection layer reads the size and the device of its convolution's output:

def forward(self, p, out):
    bs, _, ny, nx = p.shape                              # read from the convolution's output
    self.grid = self.create_grids((nx, ny), p.device)    # stores nx and ny on the module

The stores into the module happen after the graph, and they need p.shape and p.device. So the three convolution outputs were results of the graph for no other reason than to be asked for their size afterwards. Inductor therefore wrote each of them twice, once more in PyTorch's own layout (68, 19 and 7 microseconds), and the CUDA-graph wrapper copied 16 MB more per call.

Change, in the Rust engine. The engine compiles a graph once for each combination of input sizes and types it meets. A value that is computed after the graph, is the same for every call of one such combination, and cannot change (a number, a string, a device, a dtype, the sizes of a tensor, a tuple of these) is now kept with the compiled graph. Its instruction does not run, and the tensor it was read from is no longer a result. The kernels of a call went from 2,600 to 2,465 microseconds.

Two fixes in the same snapshot, both found by a probe script the agent wrote for itself. A process that had not run the model in eager first showed torch.meshgrid's once-only warning inside the first call the engine watched. The Python frames that print a warning made that call look as if it entered other Python code, and the path ended there for good: a graph of 205 operations and pieces, 2,300 images/s. Frames entered to show a warning are now counted apart. And a weight that had moved twice, and was therefore copied, had stopped the early start of step 2 for good; it no longer does.

The number. 3,218 is the highest row of torch.vm that passes every check, and its agent could not get it again (below).

5. The fast configuration: weight layouts kept, large results handed out 3,338 images/s at 117 minutes, 3,384 at 168; later samples 3,353 to 3,378

Two options, both off by default, each of which gives something up. Like the other side, the agent recorded them as a second configuration and kept the first.

weight_layout="keep" (the 3,338 row). The compiled code copies the 38 weights of the 3x3 convolutions into channels last on every call: 116 microseconds. With the weights converted beforehand, in an experiment, the callable ran 5% faster. The option hands those weights to Inductor as extra inputs that are already laid out channels last. For a 1x1 weight that is a view of the same memory, which is always right. For the others it is a copy that is kept, and made again when the weight is another tensor or its version counter has moved. PyTorch raises that counter on every in-place operation, so w.mul_(), w.copy_() and writes through a view are followed. What it gives up: a write through w.data raises no counter and is not followed. The probe made for this page confirms that, on all seven states that use the option.

Why not make that safe. The agent looked at a fingerprint of each weight computed on the GPU on every call: 130 to 160 microseconds, as much as the copies it would save (144 in the same setup). A counter of writes on the memory itself would need C++.

hand_out=True (the 3,384 row, where it was always on, and as an option from the next row). Copying the results out of the recording takes about 40 microseconds. With the option, a result of 1 MB or more is handed out as a tensor on the recording's memory. Before the recording runs again it looks at the reference counts of that tensor and of its memory: if somebody still holds the tensor, the tensor is given memory of its own first; while a view of it is alive, the recording does not run at all and the compiled function does. What it gives up: somebody who kept the raw address of such a result (a DLPack capsule, __cuda_array_interface__) is invisible to reference counts and sees the next call write that memory. The 3,384 row's note names only the .data hole; the journal names both, and the later rows' notes do.

What the probes made for this page found. On the six states that hand results out, a result kept through DLPack capsules across two calls with other inputs came back with two of its four tensors changed: by their sizes, the two raw head outputs above 1 MB. The third is smaller and is copied, and the concatenated detections are made after the graph and are a new tensor in every call. Kept as tensors, all four stayed what they were, which is what the reference counts are for. On the state with only the kept weight layouts (the 3,338 row) both probes pass.

The same snapshot moved the address check of step 2 into the engine: one call for all tensors read in place, 3.4 microseconds in front of the launch instead of 23.

The safe configuration on the later sources, and the 3,218 that did not come back 3,145 to 3,162 images/s, nine rows from 124 minutes on

After each change to the source the agent measured the configuration of step 4 again, with both options off. All nine rows are between 3,145 and 3,162, 2% below the 3,218 of the same configuration at 78 minutes.

What the agent checked. The snapshot of the 3,218 row, run again through the benchmark script later: 3,125. Its own timing loop had given 3,110 to 3,130 for this configuration all along, also at the time of that row. Only the processes of two minutes around that measurement were about 3% faster (2,365 microseconds of GPU time from the launch, against 2,408 to 2,450). A GPU that had been idle and cool made no difference, and neither did an empty compile cache. Its summary: "I did not find the cause."

So the record says 3,218 for a state that passes every check, and the level this configuration held afterwards is about 3,150. Both are on the page.

A setting: more launch configurations for the generated kernels 3,353 and 3,159 images/s at 254 and 259 minutes: no gain

torch._inductor.config.max_autotune_pointwise = True lets Inductor try more launch configurations for its own kernels. In the agent's loop the batch norm and LeakyReLU kernels took 553 microseconds instead of 577 to 580, +0.7% over two rounds. In the official rows nothing shows (fast 3,353 after 3,355; safe 3,159 after 3,152). It stayed in the configuration because it never measured slower. On the other side the same setting measured 0.987.

What did not help, what was not built, and where a call's time is

Tried and dropped, with the agent's figures: cudnn.benchmark_limit = 0 (convolutions 1,519 against 1,525 microseconds); cudnn.benchmark = False (1,805 images/s); the kernels as two CUDA graphs, the second started while the first runs (2,388 to 2,410 microseconds per call against 2,356); the first convolution written out so that Inductor fuses it with its batch norm and LeakyReLU into one generated kernel (718 microseconds against 102 + 67); the deep convolutions in PyTorch's own layout to save the weight copies (58 against 30 + 12); a channels-last input buffer (3,125 against 3,164 images/s); a batch norm handed a precomputed scale and shift (no change: those kernels are bound by memory traffic).

A fix outside the benchmark. The agent's own probe registered a forward hook and removed it again. The short path recorded while the hook stood kept being tried first, so the full path was never used again: 804 images/s. The engine was like that before the run. Now a path with more operations than the one that ran last is tried first again after 16 calls, then 32, up to 1,024. The agent added 11 tests for what it built.

Not built. A hand_out that is safe: leave a result that is still held its memory, and record the graph again on new memory. In the agent's development copy this passed its whole probe at 3,182 images/s, 25 minutes before the deadline; with no time left for tests, a measurement and a check, it stayed out of the tree. And a path through zip(*list), so that the final concatenation is inside the graph.

Where a call's time is, in the agent's breakdown after step 4, for the safe configuration. A call takes 2,490 microseconds and the GPU works for 2,486 of them. The graph is on its way 125 microseconds after the call arrives; the engine's walk of the path (515 microseconds) and the CPU's part of copying the results out (110) run while the GPU works. On the GPU: convolutions 1,520 to 1,540, batch norm and LeakyReLU kernels 520 to 575, weight copies 116, copies of the results about 40.
