pytorch#198214: what "the continuation reaches no tensor" means

[precompile] Serve the continuations Dynamo never traced as plain Python. All outputs below are real, from running the stack's top commit (Python 3.12, CPU).

TL;DR. "Reaches no tensor" is shorthand for one specific check. Before Dynamo traces a frame, convert_frame calls has_tensor_in_frame(frame). If that returns False, Dynamo does not trace the frame at all and CPython runs it as ordinary bytecode. In a training step that ends with .backward(), the leftover bit of the function after the graph break is just "pop None and return". Nothing in that frame is a tensor or a module, so Dynamo skips it. The precompile artifact used to treat that skipped frame as a coverage gap and raise on it. #198214 runs it as the plain Python it always was.

1. A graph break splits the function in two

The function being captured:

SCALE = 2.0

def step(model, x):
    (model(x) * SCALE).sum().backward()

Dynamo can't put .backward() inside a graph, so it graph-breaks there. It splits step into two frames:

Entry frame: step

Traced by Dynamo. The graph is model(x) * SCALE then .sum(). Then it calls .backward() in eager and jumps to the continuation, passing along whatever values the rest of the function still needs.
→

Continuation: torch_dynamo_resume_in_step_at_9

A new function Dynamo generates holding "the rest of step after the break". Here "the rest" is only discard backward()'s return value and return None.

Every continuation is its own Python frame, and Dynamo decides whether to compile it the same way it decides for any other frame. That decision is where "reaches no tensor" comes in.

1b. "But backward is an autograd.Function that gets compiled eagerly or lazily?"

Yes, and that doesn't conflict with the graph break. There are two different things here that are both called "backward":

So a served call does this:

  1. The entry frame runs its compiled forward graph. The loss it returns has grad_fn = CompiledFunctionBackward.
  2. The entry frame's rewritten bytecode calls loss.backward() in eager. That is the graph break. The autograd engine walks to CompiledFunctionBackward, which runs the compiled backward graph (tangents_1 = ones for a scalar loss). That graph belongs to the entry frame's variant and is shipped inside it.
  3. Then the entry frame jumps to the continuation with .backward()'s return value (None).

All the compiled gradient work happens in steps 1 and 2 and belongs to the entry frame. The continuation in step 3 is only what's textually after the .backward() line in step, and here that is nothing. That's why it has no tensor. It's also why precompile's _capture_config forces eager backward lowering: a capture that never calls .backward() would otherwise never lower the backward graph, and the artifact would have no backward to ship.

2. What the continuation actually receives

Dynamo passes a continuation only the values that are still live, meaning used later in the function, plus whatever was on the Python value stack at the break. After .backward(), step never touches model or x again, so they are not passed. I hooked has_tensor_in_frame and printed each frame's locals as Dynamo saw them:

== step
  has_tensor_in_frame(step) -> True;  f_locals={'model': 'Linear', 'x': 'Tensor'}
  has_tensor_in_frame(torch_dynamo_resume_in_step_at_9) -> False;
      f_locals={'__nested_resume_fns': 'list', '__nested_frame_values': 'list', '___stack0': 'NoneType'}

The continuation's only locals are two bookkeeping lists (empty here) and ___stack0, the value .backward() returned, which is None. There is no tensor and no module among them.

3. The check itself: has_tensor_in_frame

torch/_dynamo/convert_frame.py:405. A frame counts as worth compiling if any of these hold:

RuleWhat it looks atContinuation in step
aThe code object was decorated directly with torch._dynamo.optimizeno
bSome name in co_names resolves, in the frame's globals, to the torch module (or a torch.* submodule, or numpy) no
cSome local is a Tensor or nn.Module, looking recursively inside lists, tuples, dicts and namedtuples no

Rule b needs a caveat. The continuation's co_names are ('SCALE', 'sum', 'backward'), but SCALE is a float and sum/backward are attribute names, not globals, so none of them is the torch module. All three rules fail, so convert_frame returns before tracing. Because the frame was never traced, it was never given a compile id and has no guarded code: nothing was compiled, so there is nothing to guard. CPython just runs the bytecode.

So "reaches no tensor" really means "has_tensor_in_frame said no": no tensor or module among the frame's locals, and no reference to the torch module.

5. The contrast: a continuation that does reach a tensor

Make the tail use the model, and the continuation gets compiled like any other frame:

def step_live(model, x):
    (model(x) * SCALE).sum().backward()
    return model.weight.grad.norm()
== step_live

Now model is still live after the break, so it is passed to the continuation. Rule c matches, and Dynamo traces the frame and records one guarded variant. #198214 doesn't affect this case.

6. Why this mattered for precompile

A Dynamo precompile artifact is standalone: the generated python_code rebuilds every captured frame from its record and dispatches each call by checking guards. The package keeps a record for the skipped continuation anyway, because the entry frame's rewritten bytecode does LOAD_GLOBAL torch_dynamo_resume_in_step_at_9, and that name has to be bound to something. The record is:

Why running it uncompiled is safe

A frame is marked trivial only if Dynamo skipped it on every capture call. If any call had put a tensor into that continuation, Dynamo would have compiled it, the frame would have a compile id, and it would not be trivial. So at serve time it does exactly what it did during capture, which is exactly what eager does. Two cases are deliberately unchanged: a continuation Dynamo did compile but kept no variant of (a real gap, still refused when a call reaches it), and an entry frame with nothing compiled (still refused).

7. Caveat: "no tensor" is looser than it sounds

Rule b means that just naming the torch global is enough to get a frame compiled, even with no tensor in sight. Write the same step with torch.sum:

def step_torch_global(model, x):
    torch.sum(model(x) * SCALE).backward()

The continuation's copied body contains LOAD_GLOBAL torch, so has_tensor_in_frame returns True even though the code that actually runs after the jump is still just "pop and return". Dynamo traces it and gets an empty graph. Under a precompile capture, allow_empty_graphs keeps that empty graph as a real guarded variant, so this continuation is not trivial. It is served through the ordinary guarded path, and #198214 isn't involved:

step_torch_global: FRAMES=[('step_torch_global', 1), ('torch_dynamo_resume_in_step_torch_global_at_9', 1)]
                   returned=None grads_match=True

Both spellings serve correctly. They just take different paths: the method spelling (.sum()) gives a trivial continuation served as plain Python, and the torch.sum spelling gives an empty compiled variant.

Where the change lives

  • torch/_precompile.py, _multigraph_frames: adds the "trivial" field to each frame record.
  • torch/_precompile_driver.py, _build_multigraph_forward: for a trivial non-entry frame, rebuilds a plain function instead of refuse.
  • torch/_precompile.py, _serving_mode: counts a trivial frame as covered. Nothing in the library calls this function in this stack (there is no installed serving mode here); only tests do.
  • test/test_precompile.py, test_trivial_continuation_is_served_as_plain_python.
