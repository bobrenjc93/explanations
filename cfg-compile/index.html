torch.cfg_compile: a control-flow-graph compiler for PyTorch, measured against torch.compile

A prototype that compiles the bytecode of a Python function to one control-flow graph, runs it in a Rust VM and hands the tensor work to Inductor: what was built over 86 draft PRs, how it compares with torch.compile on TorchBench in accuracy, speed, compile time and memory, where it is ahead, where it is behind, and what to do next. Nov 11 to Nov 16, 2026.

TL;DR. torch.cfg_compile is a prototype of a different front end for PyTorch's compiler. It turns the bytecode of a function into one control-flow graph in SSA form, runs that graph in a VM written in Rust, traces on real tensors, and hands the tensor work of each path through the graph to AOTAutograd and Inductor, the compiler torch.compile uses behind Dynamo. It exists as a stack of 86 draft pull requests against pytorch/pytorch, about 27,000 lines.

On the TorchBench models that run on this CPU box, it takes 0.73 of the time of torch.compile for inference (61 models) and 0.83 for training (48 models), geometric means. That is 1.90x and 1.41x eager, where torch.compile is 1.40x and 1.17x. Its outputs agree with eager's as closely as torch.compile's do, and it compiles in less time.

Three things produce the margin, all of them new in the last round and none of them in a kernel: the compiled function keeps the memory of a call for the next one, the weights of a model are built into the graphs of inference behind a check on every call, and matrix products with one row are rewritten so that they use every core. It is a margin over torch.compile with its defaults. Given an allocator that keeps memory and its own freezing switch, torch.compile is level on most models, because the kernels are the same.

It is behind on memory in training for a few models (the worst holds 18 GB where torch.compile holds 4 GB), on models whose call takes under a few milliseconds, on plain Python in the VM, and in everything that was not built or not measured: CUDA, the optimizer step, generators, sizes that only data decides.

1. What it is

torch.compile traces a function symbolically: Dynamo interprets the bytecode on stand-ins for the values, builds an FX graph of the tensor operations, and where it meets something it cannot put in a graph (a branch on the data of a tensor, a call it does not model, a side effect) it ends the graph, runs that piece in the interpreter and starts another graph behind it. Guards on everything the trace looked at decide whether a compiled piece may be used again.

torch.cfg_compile starts from the other end. The whole function is compiled, once, to a control-flow graph whose instructions are the Python operations themselves; a branch on a tensor is a branch of that graph, a side effect is an instruction, and nothing ends anything. What gets specialized is a basic block at a time, from what its first run on real inputs did:

FrontendCPython 3.12 bytecode to a control-flow graph in SSA form. Inlining and loop unrolling are transforms of that graph.
→
VM, three tiersA generic tier runs any block. A profiling run records what each tensor operation dispatched to. The specialized tier calls those kernels directly, below the Python bindings, under guards.
→
RegionsWith backend="inductor": a run of instructions, and the path its trace takes through the blocks after it, is traced on fake tensors to one ATen graph.
→
AOTAutograd + InductorThe same backend as torch.compile: forward and backward compiled; a training region returns one compiled autograd function.

Two decisions shape everything else. First, the VM measures: compiled code is timed against the interpreter on the user's own calls, and what the interpreter runs faster is handed back to it (#204861, #204878), which is why compiling a function rarely makes it slower than it was. Second, a region is tried from the outside in: the region around model(x) first, and only where an instruction does not trace is it split and the VM descends into what that instruction calls. Control flow that depends on data stays control flow of the VM, with compiled regions on either side.

2. The path: four versions of the graph backend

The VM came first and took the first three of the six days: the language, the fidelity to CPython, the measured choice between VM and interpreter. The comparison with torch.compile starts with the graph backend, which went through four versions. Each was benchmarked on the same 61 models; the numbers of the earlier versions are from their own runs on a shared machine, so read the trend, not the second decimal.

3. Results on TorchBench

Setup. TorchBench, run the way benchmarks/dynamo/torchbench.py runs it: the module and example inputs of each model; inference under no_grad in eval mode; a training step of zero_grad, forward, reduce_to_scalar_loss, backward and an SGD step. The same function goes to torch.compile(fn) and to torch.cfg_compile(fn, backend="inductor"), with default options for both. CPU only (AMD EPYC 7R13), 4 threads per run, pinned to 4 physical cores; every (model, test, compiler) in a process of its own with an empty Inductor cache, so compile times are cold. PyTorch main of Nov 9, 2026 plus the stack, Python 3.12.14.

Of TorchBench's 104 models, 61 load and run in eager mode here for inference and 49 for training; the others need datasets, TorchScript or CUDA and are left out for both compilers. Both compilers ran all 61 for inference and 48 of the 49 for training (opacus_cifar10 fails for both: the harness compares against a deep copy of the model, and Opacus' hooks do not survive the copy).

Alone or in turns. The harness measures twice: each compiler in its own process, and, inside the cfg_compile process, the two compiled functions called in turns. While both ran the same code, in turns was the number to trust, because two processes on a shared machine differed by more than the compilers did. With v4 that reversed: torch.compile is slower in a process that cfg_compile has allocated in than in a process of its own wherever page faults matter (mobilenet_v3_large: 157 ms there, 109 ms alone), which flatters cfg_compile. So the final run was made on an idle machine and this page reads the alone numbers; both are in the table views, and the geometric means of the two are close (0.73 and 0.74 for inference, 0.83 and 0.81 for training).

4. Where the margin comes from

Three changes, each of which the control-flow-graph design made a natural default rather than a setting.

Memory that belongs to the compiled function

A model allocates the same tensors on every call. glibc gives the large ones back to the system as soon as they are freed, so the next call maps them again and the kernel faults every page in: 2.67 microseconds per fault on this (virtual) machine. For a convolutional model that is more time than is left to win in its kernels. The code torch.compile itself makes for resnet50 runs in 734 ms instead of 937 ms when the allocator under it keeps the memory; mobilenet_v2 in 54 ms instead of 102 ms.

A graph compiler has nowhere to keep that memory. A compiled function does: it is what the user calls again and again with inputs of the same sizes. Every compiled function now has a workspace (#205043, #205044): while it runs, the CPU tensors made on its thread, by a compiled region, by a kernel the VM calls or by the backward, take their memory from it and give it back to it, and the next call finds blocks of the sizes it needs. No graph backend is needed to see the effect:

conv1, conv2 = torch.nn.Conv2d(3, 64, 3, padding=1), torch.nn.Conv2d(64, 64, 3, padding=1)
def f(x):
    return conv2(torch.relu(conv1(x))).mean()
g = torch.cfg_compile(f)                 # no backend: the eager kernels
x = torch.randn(32, 3, 128, 128)
# per call, 4 threads:   eager 323 ms    g 138 ms    g with keep_memory=False 302 ms

This is where most of the margin is: basic_gnn_gin 0.34, pyhpc_turbulent_kinetic_energy 0.35, basic_gnn_sage 0.35, phlippe_densenet 0.36, basic_gnn_gcn 0.46, mnasnet1_0 0.50, squeezenet1_1 0.51, densenet121 0.52, mobilenet_v2 0.54 of torch.compile's time, and all of the margin in training, where weights cannot be built in.

Weights built into the graph, behind a check

With the parameters as inputs of a graph, Inductor cannot fold a batch norm into the convolution before it or lay convolution weights out the way the kernels want them. torch.compile has a switch for that, torch._inductor.config.freezing, off by default for a reason: nothing checks that the weights stay what they were, so it is a promise the user makes.

A compiler that already keeps variants of a region behind checks can make it the default. In a call of inference (no gradients recorded, every module in eval mode) the parameters and buffers a region's graph uses are compiled into it (#205046 to #205051). Every call then checks a stamp over the object, the memory address and the version counter of each such tensor: 4 microseconds for the 320 tensors of resnet50. The version counter alone is not enough, since p.data.mul_(2) changes the memory without advancing it, so each built-in tensor also gets a lazy clone that is never read: its storage becomes copy-on-write, and PyTorch moves the tensor to other memory before anything writes to it, which the stamp sees. A tensor that changed becomes an input of the region's next graph; the rest stay built in.

resnet50 in one process, each compiler with its own copy of the model: torch.compile 1013 ms, torch.compile with freezing 799 ms, cfg_compile 675 ms. Matrices that a graph only multiplies with or looks rows up in are left as inputs (#205050): nothing folds, and a copy of them cost hf_Bert 400 MB.

One-row matrix products

A decoder that makes one token at a time multiplies a single row of activations with every weight matrix of the model. MKL runs mm of a 1×K row with a K×N matrix on one core however many threads it has, and since the matrices do not fit the cache, that core waits for memory. Rewritten as (matrix * row.T).sum(0) before the graph goes to Inductor (#205045), the product is a loop Inductor splits over the cores. A 768-to-32,128 output layer on one row: eager 7.3 ms, torch.compile 6.8 ms, cfg_compile 2.5 ms. hf_T5_generate takes 1.64 s against 3.45 s. This one is a graph rewrite that any front end could do.

What torch.compile does when asked

Two of the three are things torch.compile can be given by hand: glibc can be told to keep what is freed (MALLOC_TRIM_THRESHOLD_, MALLOC_MMAP_THRESHOLD_, MALLOC_TOP_PAD_), and freezing can be switched on. In a process set up that way, with the calls of the compilers in turns:

What "matches" does not cover. A region checks its inputs (tensors, modules and their structure, values, modes) and what its own path read from modules and globals. It does not check what a callee that the trace ran in the interpreter read from an object that is not an input. Dynamo guards those reads; this does not yet.

"Compile time" is what each compiler reports for itself: Dynamo's compile_inner, and tracing plus backend per region. The backend is the same and is most of it. What differs is the front: a region is traced by running its instructions once on fake tensors, which costs one eager call on fake tensors, and its guards are a description of its inputs rather than a tree built while tracing. "Time to steady state" is what the calls before the timed ones cost over the same number of steady calls; for cfg_compile that includes the calls it spends measuring compiled code against the interpreter, which is why it gives back in training what it saves on compiling.

Graph counts differ most where control flow or side effects sit between tensor code. hf_BigBird is 28 graphs for torch.compile and 1 here; in training, mobilenet_v2_quantized_qat is 49 against 1. It goes the other way too: hf_Bart trains as 22 graphs here against 11, and demucs as 17 against 6, where an instruction inside the model does not trace and the pieces around it become regions of their own.

7. What it costs: memory

The workspace holds what a call freed for the next call: up to one and a half times what the call had in use at its peak, on top of what is in use. In inference that is modest: the process of resnet50 grows by 566 MB over its calls, against 224 MB for torch.compile (406 MB with freezing); hf_Bert by 219 MB against 192 MB. In training it is usually about the same as torch.compile, and on a few models far more:

Over these 35 models the geometric mean is 1.07. The outliers are models whose step makes and frees many large tensors of different sizes: hf_Reformer 18 GB against 4 GB, demucs 60 GB against 36 GB, vgg16 11 GB against 7 GB, pytorch_unet 5 GB against 4 GB. The memory is held, not lost (demucs sat at 55.7 GB for the eight minutes it was watched), but it is too much, and section 11 says what to do about it.

9. Ahead, level, behind

Ahead

  • Convolutional models, from memory and built-in weights: phlippe_densenet 0.36, mnasnet1_0 0.50, squeezenet1_1 0.51, densenet121 0.52, mobilenet_v2 0.54, mobilenet_v3_large 0.55, resnet50 0.68, shufflenet_v2_x1_0 0.75, resnet152 0.82, vgg16 0.85, alexnet 0.88.
  • Models with large temporaries (graph networks, stencil codes): basic_gnn_gin 0.34, pyhpc_turbulent_kinetic_energy 0.35, basic_gnn_sage 0.35, basic_gnn_gcn 0.46, pyhpc_isoneutral_mixing 0.49.
  • Generation loops: hf_T5_generate 0.48, cm3leon_generate 0.61.
  • Models that are many graphs under Dynamo: hf_BigBird 0.65 (1 graph against 28).
  • Rarely slower than eager: torch.compile is more than 5% slower than eager on 6 inference models (doctr_reco_predictor, functorch_dp_cifar10, microbench_unbacked_tolist_sum, ...) and 5 training models; cfg_compile on none for inference and one for training (microbench_unbacked_tolist_sum), because it times compiled code against the interpreter and keeps the faster.
  • Training: mobilenet_v2_quantized_qat 0.48, pytorch_unet 0.48, hf_Reformer 0.60, basic_gnn_gin 0.62, basic_gnn_sage 0.63, squeezenet1_1 0.65, basic_gnn_gcn 0.67, nvidia_deeprecommender 0.69.
  • Compile time: 9.9 s against 13.7 s for inference, 13.8 s against 22.5 s for training.
  • Safety of the fast path: built-in weights are checked on every call; a write through .data is seen.

Level, or nearly

  • Transformers on batches, whose time is in BLAS, gain a few percent at most: hf_T5_large 0.94, hf_Bert_large 0.95, hf_Bert 0.96, llava 0.98, hf_GPT2_large 0.98, llama 0.98, moondream 1.00, hf_distil_whisper 1.01.
  • Against a tuned torch.compile (allocator that keeps memory, freezing on): within a few percent on most convolutional models.
  • Accuracy: both within float rounding of eager for inference.
  • Time to steady state in training: 29.6 s against 29.6 s.

Behind

  • Memory in training on a few models: hf_Reformer 18 GB against 4 GB, demucs 60 GB against 36 GB.
  • Very short calls: lennard_jones (0.27 ms against 0.25 ms) is 1.10 alone and 1.04 in turns, and soft_actor_critic (2.4 ms) no better than level (1.02); entering a region costs a walk over its arguments in Python.
  • One training model: resnet152 at 1.06 alone (0.98 in turns).
  • Plain Python in the VM: three to four times slower than CPython when forced; hidden by handing it back.
  • The optimizer step is not compiled; torch.compile compiles it.
  • Guards: reads made by interpreted callees from objects that are not inputs are not checked.
  • Not built: generators, coroutines, except*; sizes that only data decides; Python other than 3.12.
  • Not measured: anything on CUDA. The workspace is for CPU memory only.
  • Maturity: six days old; 81 of the 86 PRs have had neither review nor CI.

10. What went wrong on the way

Most of the errors were in measuring, and several flattered the prototype until they were found. They are listed because the final numbers are only as good as the list is complete.

  • A shared kernel cache. Inductor's on-disk cache is shared between processes, so whichever compiler ran second found the kernels the first had built. The first run's "7.5 s against 4.3 s" compile time was that; cold, resnet50 was 17.4 s against 15.2 s. Every process now gets an empty cache (#204943).
  • Timing before the measurement had settled. Calls were timed while cfg_compile was still comparing compiled code with the interpreter, which made it look slower than it was. The harness now waits (#204941).
  • Wrappers left on nn.Module. An early version wrapped methods of nn.Module process-wide; with them torch.compile failed on one model in the same process and ran 2% slower on another, which flattered the comparison. Removed (#204948).
  • A cache that grew, with the right answer. An object made inside a trace was handed out again on every call, so T5's key-value cache grew across calls to generate while the tokens stayed correct. Found from a profile showing the same kernel at 514 µs and 6 µs (#204984).
  • A benchmark model with no weights. cm3leon_generate is built without initializing its weights: 2.6 GB of zeros in memory that was never written, which the kernel serves from one 4 KB page. Every compiler looked faster on it than a model with weights allows (eager 5.7 s; 9.9 s once the weights are written), and it made the one-row rewrite look like 0.43 where it is 0.61. The harness now writes every weight once (#205088).
  • Weights copied on every decoder step. A small region had built in 145 matrices it never used; the decoder-step graph read the same matrices through writable pointers, so each was copied on every step, and the measurement gave up on the compiled code. Only what a graph uses is built in now.
  • Too many workers for the container. Nine training processes at once went past the 256 GiB of the container the benchmark ran in, which killed it as a whole, four times, before the cause was understood. The harness now reads the cgroup limit, starts nothing above a fraction of it, and stops its own largest process above a second mark (#205096). The final run peaked at 161 GiB.
  • A leak, found by that guard. The first process the guard stopped was hf_Bart's training under cfg_compile, at 55 GB where eager peaks at 8 GB. A region that is handed a loss module built inside forward, as every model of transformers does, made a variant per step, and each variant kept that step's logits alive: 393 MB per step. Fixed, with the price that the small region around such a loss now runs uncompiled (#205102, #205103).
  • Tests that passed without the feature. Small functions are inlined into the compiled function, so three new tests never exercised the code they were written for. Every new test is now run against the parent commit, and must fail there.

11. Suggested next steps

  1. Bound what the workspace holds. Limit the sum of what is in use and what is kept to about 1.25 to 1.5 times the peak, accept a kept block only if it is at most a quarter larger than the request (it is twice now), and evict on a miss. This needs re-measuring densenet121, hf_T5_generate, hf_Reformer and demucs, since the same slack is what makes those fast. It is the one known cost that should not ship as it is.
  2. Keep the loss region of transformer models compiled. Name a module that has no tensors by its class and attribute values instead of its identity, so that a loss built on every call is one variant and not one per call. The leak fix retires that region instead, which is safe and gives up a little speed on every HuggingFace training step.
  3. Measure on CUDA. Nothing here says what happens on a GPU. Built-in weights and fewer graphs carry over; the workspace does not (the CUDA allocator already caches), and page faults are not the bottleneck there, so the margin is unknown and probably smaller.
  4. Look for more kernels that do not use the machine. With memory and weights handled, what is left on the CPU is in the kernels: BLAS for transformers on batches, MKLDNN for convolutions. The one-row product was found by asking, per kernel, how many cores it used. A profile of every model in that form would find the others, if there are any.
  5. Close the guard gap. Trace callees through the VM's own graphs instead of running them in the interpreter during a trace, so that every read is seen and guarded. This is the main soundness difference from Dynamo.
  6. Compile what training still leaves to the interpreter. The optimizer step, and frames that C++ enters (a custom autograd.Function's forward, as in hf_Reformer), which the VM cannot see today.
  7. Make the VM fast on Python, or keep handing it back: inline caches for attribute loads and method calls are the first candidates.
  8. Move the walk over a region's arguments into Rust. It is 0.4 ms per decoder step of T5 and the reason very short calls are behind.
  9. Review and land from the bottom. The five PRs with CI are the dispatcher hook; everything above depends on a decision about whether this front end is wanted. Several PRs above are larger than a reviewer should be asked to read.
  10. Report the cm3leon_generate finding upstream. A benchmark whose weights are unwritten zeros reads one page of the kernel over and over, for every compiler.
