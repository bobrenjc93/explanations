torch.rewrite: a function as a control-flow graph and a list of rewrites, measured against torch.compile

A prototype that compiles the bytecode of a Python function to one control-flow graph, runs it in a Rust VM and hands the tensor work to Inductor: what was built over 129 draft PRs, how it compares with torch.compile on TorchBench and on the perf dashboard's suites in accuracy, speed, compile time and memory, where it is ahead, where it is behind, and what to do next. Nov 11 to Nov 18, 2026.

TL;DR. torch.rewrite is a prototype of a different front end for PyTorch's compiler. It turns the bytecode of a function into one control-flow graph in SSA form, runs that graph in a VM written in Rust, traces on real tensors, and hands the tensor work of each path through the graph to AOTAutograd and Inductor, the compiler torch.compile uses behind Dynamo. It exists as a stack of 129 draft pull requests against pytorch/pytorch, about 35,000 lines. It was called torch.cfg_compile until the sixth version, which renamed it for what the one who calls it does: hand over a function and a list of rewrites.

On the TorchBench models that run on this CPU box, it takes 0.73 of the time of torch.compile for inference (61 models) and 0.82 for training (48 models), geometric means. That is 1.82x and 1.43x eager, where torch.compile is 1.33x and 1.17x. Its outputs agree with eager's as closely as torch.compile's do, and it compiles in less time.

Three things produce the margin, none of them in a kernel: the compiled function keeps the memory of a call for the next one, the weights of a model are built into the graphs of inference behind a check on every call, and matrix products with one row are rewritten so that they use every core. It is a margin over torch.compile with its defaults. Given an allocator that keeps memory and its own freezing switch, torch.compile is level on most models, because the kernels are the same.

It holds more memory: 1.02 times what the process of torch.compile holds at its peak in training and 1.02 times in inference (geometric means; the last version had single models at four times). It is behind on models whose call takes under a few milliseconds, on plain Python in the VM, and in everything that was not built: generators, modules with hooks.

On a GPU (one H100, the three suites of the PyTorch perf dashboard at its settings) it takes 0.91 of the time of torch.compile for inference over 86 models, and 0.97 of the time of torch.compile with its freezing switch, which is the fair comparison there. It pays for that in memory: 1.59 times the peak GPU memory of torch.compile while a model is warmed up and compiled. For training it takes 0.99 of the time of torch.compile over 75 models. The GPU numbers this page had before Nov 18 were measured on a build of PyTorch without cuDNN (section 9).

The sixth version also made what is done to a function one list of passes, to which a user adds passes of their own, in Python or in Rust; rewrites the functions that C code calls (constructors, properties, operators, callbacks), through the frame hook Dynamo uses; and runs on CPython 3.14 as well as 3.12.

A rewritten function also behaves like an interpreted one where tools look: its frame has its variables, so tracebacks, debuggers, eval and exec see them, and of 27,028 tests of CPython's own suite five end differently under the compiler, where it was 21.

1. What it is

torch.compile traces a function symbolically: Dynamo interprets the bytecode on stand-ins for the values, builds an FX graph of the tensor operations, and where it meets something it cannot put in a graph (a branch on the data of a tensor, a call it does not model, a side effect) it ends the graph, runs that piece in the interpreter and starts another graph behind it. Guards on everything the trace looked at decide whether a compiled piece may be used again.

torch.rewrite starts from the other end. The whole function is compiled, once, to a control-flow graph whose instructions are the Python operations themselves; a branch on a tensor is a branch of that graph, a side effect is an instruction, and nothing ends anything. What gets specialized is a basic block at a time, from what its first run on real inputs did:

FrontendCPython 3.12 bytecode to a control-flow graph in SSA form. Inlining and loop unrolling are transforms of that graph.
→
VM, three tiersA generic tier runs any block. A profiling run records what each tensor operation dispatched to. The specialized tier calls those kernels directly, below the Python bindings, under guards.
→
RegionsWith backend="inductor": a run of instructions, and the path its trace takes through the blocks after it, is traced on fake tensors to one ATen graph.
→
AOTAutograd + InductorThe same backend as torch.compile: forward and backward compiled; a training region returns one compiled autograd function.

Two decisions shape everything else. First, the VM measures: compiled code is timed against the interpreter on the user's own calls, and what the interpreter runs faster is handed back to it (#204861, #204878), which is why compiling a function rarely makes it slower than it was. Second, a region is tried from the outside in: the region around model(x) first, and only where an instruction does not trace is it split and the VM descends into what that instruction calls. Control flow that depends on data stays control flow of the VM, with compiled regions on either side.

3. Results on TorchBench

Setup. TorchBench, run the way benchmarks/dynamo/torchbench.py runs it: the module and example inputs of each model; inference under no_grad in eval mode; a training step of zero_grad, forward, reduce_to_scalar_loss, backward and an SGD step. The same function goes to torch.compile(fn) and to torch.rewrite(fn, backend="inductor"), with default options for both. CPU only (AMD EPYC 7R13), 4 threads per run, pinned to 4 physical cores; every (model, test, compiler) in a process of its own with an empty Inductor cache, so compile times are cold. PyTorch main of Nov 9, 2026 plus the stack, Python 3.12.14.

Of TorchBench's 104 models, 61 load and run in eager mode here for inference and 49 for training; the others need datasets, TorchScript or CUDA and are left out for both compilers. Both compilers ran all 61 for inference and 48 of the 49 for training (opacus_cifar10 fails for both: the harness compares against a deep copy of the model, and Opacus' hooks do not survive the copy).

Alone or in turns. The harness measures twice: each compiler in its own process, and, inside the torch.rewrite process, the two compiled functions called in turns. While both ran the same code, in turns was the number to trust, because two processes on a shared machine differed by more than the compilers did. With v4 that reversed: torch.compile is slower in a process that torch.rewrite has allocated in than in a process of its own wherever page faults matter (mobilenet_v3_large: 157 ms there, 109 ms alone), which flatters torch.rewrite. So the final run was made on an idle machine and this page reads the alone numbers; both are in the table views, and the geometric means of the two are close (0.73 and 0.74 for inference, 0.82 and 0.80 for training).

4. Where the margin comes from

Three changes, each of which the control-flow-graph design made a natural default rather than a setting.

Memory that belongs to the compiled function

A model allocates the same tensors on every call. glibc gives the large ones back to the system as soon as they are freed, so the next call maps them again and the kernel faults every page in: 2.67 microseconds per fault on this (virtual) machine. For a convolutional model that is more time than is left to win in its kernels. The code torch.compile itself makes for resnet50 runs in 734 ms instead of 937 ms when the allocator under it keeps the memory; mobilenet_v2 in 54 ms instead of 102 ms.

A graph compiler has nowhere to keep that memory. A compiled function does: it is what the user calls again and again with inputs of the same sizes. Every compiled function now has a workspace (#205043, #205044): while it runs, the CPU tensors made on its thread, by a compiled region, by a kernel the VM calls or by the backward, take their memory from it and give it back to it, and the next call finds blocks of the sizes it needs. No graph backend is needed to see the effect:

conv1, conv2 = torch.nn.Conv2d(3, 64, 3, padding=1), torch.nn.Conv2d(64, 64, 3, padding=1)
def f(x):
    return conv2(torch.relu(conv1(x))).mean()
g = torch.rewrite(f)                 # no backend: the eager kernels
x = torch.randn(32, 3, 128, 128)
# per call, 4 threads:   eager 323 ms    g 138 ms    g with keep_memory=False 302 ms

This is where most of the margin is: basic_gnn_sage 0.36, phlippe_densenet 0.37, pyhpc_turbulent_kinetic_energy 0.38, basic_gnn_gin 0.41, mobilenet_v2 0.44, basic_gnn_gcn 0.45, squeezenet1_1 0.47, mnasnet1_0 0.49, densenet121 0.49 of torch.compile's time, and all of the margin in training, where weights cannot be built in.

Weights built into the graph, behind a check

With the parameters as inputs of a graph, Inductor cannot fold a batch norm into the convolution before it or lay convolution weights out the way the kernels want them. torch.compile has a switch for that, torch._inductor.config.freezing, off by default for a reason: nothing checks that the weights stay what they were, so it is a promise the user makes.

A compiler that already keeps variants of a region behind checks can make it the default. In a call of inference (no gradients recorded, every module in eval mode) the parameters and buffers a region's graph uses are compiled into it (#205046 to #205051). Every call then checks a stamp over the object, the memory address and the version counter of each such tensor: 4 microseconds for the 320 tensors of resnet50. The version counter alone is not enough, since p.data.mul_(2) changes the memory without advancing it, so each built-in tensor also gets a lazy clone that is never read: its storage becomes copy-on-write, and PyTorch moves the tensor to other memory before anything writes to it, which the stamp sees. A tensor that changed becomes an input of the region's next graph; the rest stay built in.

resnet50 in one process, each compiler with its own copy of the model: torch.compile 1013 ms, torch.compile with freezing 799 ms, torch.rewrite 675 ms. Matrices that a graph only multiplies with or looks rows up in are left as inputs (#205050): nothing folds, and a copy of them cost hf_Bert 400 MB.

One-row matrix products

A decoder that makes one token at a time multiplies a single row of activations with every weight matrix of the model. MKL runs mm of a 1×K row with a K×N matrix on one core however many threads it has, and since the matrices do not fit the cache, that core waits for memory. Rewritten as (matrix * row.T).sum(0) before the graph goes to Inductor (#205045), the product is a loop Inductor splits over the cores. A 768-to-32,128 output layer on one row: eager 7.3 ms, torch.compile 6.8 ms, torch.rewrite 2.5 ms. hf_T5_generate takes 1.62 s against 3.41 s. This one is a graph rewrite that any front end could do.

What torch.compile does when asked

Two of the three are things torch.compile can be given by hand: glibc can be told to keep what is freed (MALLOC_TRIM_THRESHOLD_, MALLOC_MMAP_THRESHOLD_, MALLOC_TOP_PAD_), and freezing can be switched on. In a process set up that way, with the calls of the compilers in turns:

None of the five is in the result of a computation: one counts objects around the first call of a function that C code calls, whose rewritten form is made in between; two are a disassembly that shows which loops the interpreter's own specializer saw, one is a code object corrupted by hand, one a garbage collection that comes one object earlier. Getting from 81 to 21 was a round of its own: real frames for compiled and inlined calls so tracebacks have columns, CPython's exact error messages, locals released when the interpreter releases them, signals and thread switches inside compiled loops, a recursion limit that means the same depth. Getting from 21 to 4 was the fifth version. Seventeen of the 21 had one of two causes: the variables of a compiled function lived in the VM's registers and its frame was empty, and a trace function was not told about what compiled code called. Now every assignment also binds the variable in the frame (#205189), which is what let functions that call eval, exec or super() be compiled at all (#205190: 231 of the 246 test methods that had been turned down), and while sys.settrace is set, calls run in the interpreter (#205191). On tensor code the frame costs nothing that can be measured, because a tensor that only kernels touch is bound to its variable when something can look, not before; on plain Python loops that the VM is forced to run it costs 6 to 12%.

What "matches" does not cover. A region checks its inputs (tensors, modules and their structure, values, modes) and what its own path read from modules and globals. It does not check what a callee that the trace ran in the interpreter read from an object that is not an input. Dynamo guards those reads; this does not yet.

"Compile time" is what each compiler reports for itself: Dynamo's compile_inner, and tracing plus backend per region. The backend is the same and is most of it. What differs is the front: a region is traced by running its instructions once on fake tensors, which costs one eager call on fake tensors, and its guards are a description of its inputs rather than a tree built while tracing. 7. What it costs: memory

The workspace holds what a call freed for the next call, and the process has that memory whether or not a call is running. In the last version that was the one cost that should not have shipped: whole blocks were kept, up to one and a half times the peak of a call on top of what was in use, and single models held four times what torch.compile holds. Two changes went in (#205194, #205195), and this is where it stands:

Training, 48 models: geometric mean 1.02; the most are demucs 50.6 GB against 35.9 GB, vgg16 8.8 GB against 6.8 GB, hf_Longformer 10.4 GB against 8.2 GB, hf_Roberta_base 15.6 GB against 12.9 GB. Inference, 61 models: 1.02; the most are llama 5.1 GB against 3.1 GB, demucs 3.1 GB against 2.2 GB, dlrm 4.7 GB against 3.6 GB.

What the two changes were. The largest number of the last version, hf_Reformer at 18 GB against 4 GB, was not the workspace at all. The first times the VM runs a call of a C function it records the kernel calls underneath, to see whether the call is one kernel that it can call directly from then on, and the record kept the arguments and results of all of them alive until the call returned. torch.autograd.Function.apply is such a C function, and in hf_Reformer what runs under it is the whole reversible encoder: the first training step held every tensor of every layer at once, 18 GB, and every later step 4. A record now lets go of its tensors as soon as it sees a second kernel call. The other change is the workspace itself: instead of keeping whole blocks and handing one out when it is between the size asked for and twice that size, it cuts what is asked for out of the memory it holds, closest fit first, joins what comes back with the free memory next to it, and holds at most the peak of its tensors plus half of that, 256 MB at most. Replaying the requests of eleven models under both policies, the most that is held over the most the tensors ask for at once went from 1.55 to 1.24, and the share of a call's bytes that has to come from the system, which is what costs page faults, from 4.9% to 1.1%: less memory and no less speed.

What is left. A function still holds about the peak of its tensors between calls, where torch.compile gives everything back: that is what keeping memory means, and keep_memory=False is there for a process that cannot afford it. And the first calls of a function run before its graphs exist, one kernel at a time, and can hold more at once than the calls after them: a training step of vgg16 asks for 4.95 GB at once in its first two calls and for 3.02 GB from the third on, and the memory of the first calls stays in use because the later ones are cut out of it. A limit that follows the last few calls was tried in four variants and did not get vgg16 below 5.9 GB (6.3 GB as it is; 4.7 GB without a workspace), so it is not in the stack.

Not better everywhere. Of the 35 training models that were measured the same way in the last version, 6 hold less now (hf_Reformer 0.24 of what it held, vgg16 0.78 of what it held, demucs 0.84 of what it held) and 11 hold more (resnet152 1.17, hf_Longformer 1.13, hf_BigBird 1.10, resnet50 1.09). Keeping whole blocks suited a model whose sizes repeat exactly from call to call; cutting to size suits the others, and costs those a few percent.

9. On a GPU

What changed in this section on Nov 18. It used to report TorchBench at its default batch sizes, measured by the stack's own harness on a build of PyTorch that had been configured without cuDNN: convolutions ran PyTorch's own kernels, 20 to 30 times slower than cuDNN's. Eager, torch.compile and torch.rewrite ran on that same build, so the ratios compared like with like, but for convolutional models they were not of the workload people run. The section now reports the three suites of the PyTorch perf dashboard, run by the dashboard's runner at its settings, on a build with cuDNN 9.26. What the harness measured is kept below where it explains a change, and says so.

Everything above is a CPU. On one NVIDIA H100 (CUDA 12.8, cuDNN 9.26, Triton 3.8.0) the seventh version was measured the way the perf dashboard measures torch.compile: benchmarks/dynamo runs HuggingFace, timm and TorchBench at batch sizes of 8 to 1024, in bfloat16 for inference and under AMP for training, and times compiled calls against eager ones in turns in one process. #205357 lets that runner measure torch.rewrite (--rewrite) where --backend inductor has it measure torch.compile. The HuggingFace models that go through generate are left out (--rewrite has no path for them), and the TorchBench models that fail under both compilers on this machine.

Reading it. With weights as constants of the graph, Inductor folds batch norms into convolutions and makes one product of the three projections of an attention layer, for torch.rewrite as for torch.compile with freezing: the two then run nearly the same kernels, and timm, which is convolutions at large batches, is level (0.99). What margin there is comes from what runs around the kernels and from how many graphs a call is.

  • Ahead of torch.compile with freezing: cm3leon_generate 0.28, basic_gnn_gcn 0.51, basic_gnn_gin 0.90, phlippe_densenet 0.91 on TorchBench; T5ForConditionalGeneration 0.91, GPT2ForSequenceClassification 0.91, MT5ForConditionalGeneration 0.92, MBartForCausalLM 0.93 on HuggingFace. basic_gnn_gcn is one graph where Dynamo makes six, because a size that only data decides stays in the graph (#205326); the generation loop of cm3leon_generate stays instructions of the VM, where Dynamo ends a graph at each step that depends on data.
  • Against torch.compile as the dashboard runs it, without freezing: 0.91 of its time over 86 models; ahead on 64, behind on 2 (opacus_cifar10 2.85, pyhpc_turbulent_kinetic_energy 1.10).
  • Behind: opacus_cifar10 3.22, pyhpc_equation_of_state 1.10, llava 1.05, pyhpc_turbulent_kinetic_energy 1.04 on TorchBench, AllenaiLongformerBase 1.06 on HuggingFace, none on timm. opacus_cifar10 puts a hook on every layer; a region refuses a module with hooks, so the model runs at the speed of eager, where torch.compile compiles through them. The pyhpc models are calls of under a millisecond that the runner times right after an eager call of the same model, which costs torch.rewrite more than torch.compile: 0.099 ms against 0.084 ms for pyhpc_equation_of_state, and 0.069 ms for both when the calls are back to back. AllenaiLongformerBase is four graphs, and its encoder's graph leaves a size open that only data decides, where Dynamo ends its graph there and compiles what follows for the size it saw; that this is what costs the 9% was not measured.
  • Memory is the price: the runner records the most that was allocated on the GPU while a model is warmed up and compiled, and torch.rewrite has 1.84 times what torch.compile has there on HuggingFace, 1.41 on timm and 1.53 on TorchBench (where the smallest models hold tens of megabytes and the ratio moves with them: it was 1.33 a run earlier). The first calls of a rewritten function run the model kernel by kernel on real tensors, so its peak is never under eager's, where torch.compile never runs the model that way; and a weight that is built in is held a second time (XGLM: 6.0 GB, where it was 4.9 GB before the matrices of its products were built in).
  • Training: 0.99 of the time of torch.compile over 75 models (1.00 on HuggingFace, 1.00 on timm, 0.97 on TorchBench); ahead on 17, behind on 13 (microbench_unbacked_tolist_sum 1.40, dcgan 1.10, lennard_jones 1.08 on TorchBench, PLBartForCausalLM 1.09, YituTechConvBert 1.06, DistilBertForMaskedLM 1.06 on HuggingFace, deit_tiny_patch16_224.fb_in1k 1.05 on timm). The forward and the loss are one graph under both, and the backward is AOTAutograd's. What torch.rewrite did not have when the suites were first run was the step of the optimizer as a graph: torch.compile compiles it, and the regions pass did not look at torch/optim/. With the update a region (#205437), a step of deit_tiny takes 12.4 ms, as under torch.compile in the same process, where it took 14.3 ms. Getting there costs more: a training step is called some hundred times while its levels of calls are measured one after another, 28 s of warm-up where torch.compile compiles for 6 s (geometric means).
  • An accident of the interpreter had two models a quarter behind (how it was found is a page of its own). CPython 3.11 and 3.12 keep the frames of a thread in chunks of 16 KB and unmap a chunk the moment the frame at its start returns; 3.13 and 3.14 have kept one for reuse since March 2026, and the perf dashboard's jobs run 3.11. The code Inductor generates for a graph has one large frame and launches the graph's kernels from it. Where the runner calls tf_efficientnet_b0 for training under torch.rewrite, that frame ended 128 bytes short of the end of a chunk, and each of the 452 calls it makes in a step mapped a chunk and unmapped it again: 30.5 ms a step, and 23.3 ms with one more Python frame anywhere above. The runtime now keeps the chunks that are freed (#205502), and the numbers here are of that build. It is not torch.rewrite's accident alone. The timed loops ask for these many chunks a step: under torch.rewrite, which now has them at hand, tf_efficientnet_b0 (452), repvgg_a2 (358) in training and none in inference; under torch.compile, which maps them as it would on the dashboard, RobertaForCausalLM (507), BertForMaskedLM (503), nfnet_l0 (260), ElectraForCausalLM (256) in training and none in inference. With those four run a second time and the chunks kept for torch.compile as well, its step of ElectraForCausalLM is 12% shorter (torch.rewrite is then at 0.96 of its time, not 0.89) and those of the other three 0% to 5%; training as a whole is then at 0.990 of the time of torch.compile, where it is at 0.988 with the first runs.
  • Compile time: 11 s against 13 s on HuggingFace, 11 s against 13 s on timm, 6 s against 3 s on TorchBench (geometric means, as the runner reports them).

What the dashboard's suites found. The first run of the suites had torch.rewrite behind torch.compile with freezing on HuggingFace and timm, behind on every model whose call is short, and behind in training. Five causes, each in torch.rewrite and none in Inductor:

  1. A method of an object as what is called. The runner calls a model through runner.forward_pass, a method of an object that holds its parsed command line, 127 attributes. The pass that tells a call that is like the one before in the runtime did not know a bound method or an object with attributes, so every call described that object in Python: 52 of the 96 microseconds of a call of pyhpc_equation_of_state (#205405).
  2. A loss module in training. Weights were built in when no module of the call was in training, and the timm runner holds a CrossEntropyLoss, which is in training like any module nobody called eval() on: no timm model had its weights built in. A module in training now keeps only its own weights as inputs (#205409): tf_efficientnet_b0 went from 5.3 ms to 4.0 ms a call.
  3. The matrix of a product. A matrix that a graph only multiplies with was left as an input, to not hold it twice. On a GPU, Inductor fuses the products of one input only if their matrices are constants; they are built in there now (#205410), at the price in memory above.
  4. What stands in during a trace. maml failed: a function that stands in for torch.autograd.grad while a region is traced was handed back by a region and called (#205397).
  5. The step of an optimizer. The regions pass left torch/optim/ alone, as code that moves tensors about. The update of Adam or SGD is operations on lists of tensors, which a region holds as it is; it is a region now (#205437). A learning rate is a float in the key of that region, so one on a schedule would have been a graph per step: a region whose first calls each come with other numbers gets no graph (#205436). Under Adam the weights are no longer bit for bit the interpreter's, as they are not under torch.compile: the corrections for the first steps are float32 in the graph.

What the stack does to torch.compile. The first PR of the stack adds a check to the dispatcher, which every operator call of every program passes. The perf dashboard's own workflow (the three suites, inference in bfloat16 and training under AMP, thirteen configurations, on H100 runners) was run on the commit the stack starts from, twice, and on the top of the stack. Its build has no Rust runtime, so it measures torch.compile, not torch.rewrite. Over 681 inference and 423 training model runs the speedup over eager is within 0.3% of the starting commit's in every comparison. Compiled latency on the stack is 0.6% and 0.9% above the starting commit's first run and 0.5% and 0.1% above its second, and the second run is itself 0.2% and 0.8% above the first: within what two runs of one commit differ by. The one place where the stack is slower than both is HuggingFace for inference (0.8% and 1.5%), where the two runs of the starting commit differ by 0.7% the other way; two runs cannot tell whether that is the dispatcher.

Before the dashboard's runner: the stack's harness, on the build without cuDNN. The ratios in the rest of this section are of TorchBench at its default batch sizes in float32, each compiler in a process of its own, on that build. They are kept because they are what each change was measured by. The first run of all models on the GPU, on the fifth version, had torch.rewrite at 1.10 times torch.compile for inference. Profiling single models found three causes, none of them in a kernel, and each became a PR:

  1. A default device is a Python mode. torch.set_default_device is a torch function mode: Python is entered for every torch function called while it is active, the few hundred calls of the code Inductor generates included. A graph made under a default device is now called with the mode off the stack, as Dynamo does (#205245): llama from 1.24 to 1.03 of the time of torch.compile.
  2. Left to the interpreter too early. A callee is timed in the VM and in the interpreter and left to the interpreter if it is faster there. A callee whose region had not yet decided to become a graph ran its instructions one by one, lost that comparison, and never came back, so the region never got its graph: cm3leon_generate ran at the speed of eager with 32 callees left to the interpreter, its decoder layers among them. A region that is still deciding now keeps the measurement open (#205246): cm3leon_generate from 2.50 to 0.82 of the time of torch.compile.
  3. Three passes over a module's tensors on every call. Before its graph ran, a region read each tensor of the module out of its dict, described them all for the key of the call, and checked the ones the graph has built in: 193 of the 1,670 microseconds of a call of hf_DistilBert. One pass in Rust now checks that nothing changed since the tensors were last looked at (#205258): 118 microseconds.

That was the sixth version: level for inference in that harness (1.00). What kept it level was looked for model by model, and became the first ten PRs of the seventh version:

  1. A size that only data decides. A region with nonzero or a mask as an index in it was traced, because the trace gives such a size a symbol, and then given up as a whole: Inductor was handed the graph without the ShapeEnv the symbol belongs to. The trace is now made again in one the backend shares (#205326): basic_gnn_gcn from 1.26 to 0.58, one graph where Dynamo makes six, and hf_Reformer from 1.06 to 0.86.
  2. What a compiled call costs before its graph runs. A region made the key of every call by walking, in Python, what it was handed, after a walk over the dicts of every module to see that none had changed: 83 microseconds for a ResNet-50 with a backend that computes nothing. The dicts are now watched, so one number says that none changed (#205328); the places of the tensors are not looked at while it says so (#205329); and a call that is like the one before is told so in one pass in the runtime, which returns its key and inputs (#205330 to #205332): 21 microseconds. hf_Bart from 1.04 to 0.95, lennard_jones from 1.04 to 0.96.
  3. Objects made again by their __init__. What a model returns that a region made (a ModelOutput, a distribution) was made again on every call by its class, in the interpreter. It is a new object with the same attributes now (#205327).
  4. A clock that does not wait for the GPU. A function is left to the interpreter when it is faster there, but a kernel on a GPU is started and not waited for: a graph that waits somewhere inside looked slower than kernels that were only started. A call that is measured now ends when the GPU is idle (#205334).
  5. The same program in every mode. Dynamo turns the validation of the arguments of distributions off for its process; the harness measured eager and torch.rewrite with it on. It is off in all three now (#205335): soft_actor_critic from 1.71 to 1.03.

In that harness the seventh version took 0.95 of the time of torch.compile for inference over 59 models, where the sixth took 1.00.

10. One list of passes, and passes of your own

The entry point used to be torch.cfg_compile, with nine keywords for what it should do. It is torch.rewrite(fn, passes=[...]) now (#205237, #205238). The list is what is done to the function, in its order. With an empty list the function runs with exactly the semantics of the interpreter, so nothing is compiled: a function is handed over together with a list of rewrites, and each of them can be looked at.

torch.rewrite.canonical
# ('inline', 'unroll', 'shortcuts', 'resolve_dispatch', 'tensor_accessors', 'method_calls', 'fold', 'dce')

@torch.rewrite(passes=[torch.rewrite.inductor, *torch.rewrite.canonical])   # graphs by AOTAutograd and Inductor
def forward(model, x): ...

A kernel in place of operations. A pass sees which ATen operator each instruction was seen to be, so x.pow(2), x ** 2 and torch.pow(x, 2) are the same thing to it. torch.rewrite.swap(ops, kernel) finds a run of operators in a block, puts one call of the kernel in its place, and for the first calls runs the replaced instructions on the same inputs and compares (#205242):

def rms_norm(x, weight):
    return x * torch.rsqrt(x.pow(2).mean(-1, keepdim=True) + 1e-6) * weight

fuse = torch.rewrite.swap(["pow", "mean", "add", "rsqrt", "mul"], my_kernel)
g = torch.rewrite(rms_norm, passes=[fuse, *torch.rewrite.canonical])

# a kernel that is wrong:
# torch.rewrite.Mismatch: wrong: result 0 differs by up to 0.0217 on call 1
#   (the operations it replaced were run on the same inputs)

A pass in Rust. The same pass can be written in Rust, in a library of its author's that links against neither Python nor PyTorch and is built with plain cargo build (#205243). The kernel stays a Python object that the pass is bound to; where it goes is decided in Rust:

impl Pass for FuseRmsNorm {
    fn name(&self) -> &'static str { "fuse_rmsnorm" }
    fn run(&self, region: &mut Region<'_>, kernel: Option<Bound>) -> Result<bool, Error> {
        let Some(kernel) = kernel else { return region.fail("fuse_rmsnorm needs a kernel") };
        match region.find(&["pow", "mean", "add", "rsqrt", "mul"]) {
            Some((start, end)) => region.swap(start, end, kernel, 4),   // checked for 4 calls
            None => Ok(false),
        }
    }
}
export_passes!(FuseRmsNorm);

# Python
passes = torch.rewrite.load_passes("target/release/libmine.so")
g = torch.rewrite(rms_norm, passes=[passes["fuse_rmsnorm"].bind(my_kernel), *torch.rewrite.canonical])

Functions that C code calls. The VM used to rewrite a callee only when its own call instruction made the call. The __init__ of a class, a property, an operator, the key of sorted, a function under functools.partial and everything a generator calls ran in the interpreter, with all they called. While a rewritten function runs, the interpreter now starts its frames through a hook of the runtime (PEP 523, the mechanism Dynamo uses), and the hook runs a frame's function in its rewritten form, in the frame the interpreter made (#205240). The IR stays the VM's own: the hook is only how frames that the VM did not start come back to it. A function that takes the hook pays about 25 ns a call for it, and code that is not under a rewritten function pays nothing.

CPython 3.14. The stack was 3.12-only in three places: the pyo3 version, the instruction set the frontend knew, and the layout of interpreter frames. All three are ported (#205259 to #205263): the tests of the stack pass under 3.12 and under 3.14, and over the 181,327 functions of the PyTorch tree that exist under both, the frontend accepts and turns down the same ones.

12. What went wrong on the way

Most of the errors were in measuring, and several flattered the prototype until they were found. They are listed because the final numbers are only as good as the list is complete.

  • A shared kernel cache. Inductor's on-disk cache is shared between processes, so whichever compiler ran second found the kernels the first had built. The first run's "7.5 s against 4.3 s" compile time was that; cold, resnet50 was 17.4 s against 15.2 s. Every process now gets an empty cache (#204943).
  • Timing before the measurement had settled. Calls were timed while torch.rewrite was still comparing compiled code with the interpreter, which made it look slower than it was. The harness now waits (#204941).
  • Wrappers left on nn.Module. An early version wrapped methods of nn.Module process-wide; with them torch.compile failed on one model in the same process and ran 2% slower on another, which flattered the comparison. Removed (#204948).
  • A cache that grew, with the right answer. An object made inside a trace was handed out again on every call, so T5's key-value cache grew across calls to generate while the tokens stayed correct. Found from a profile showing the same kernel at 514 µs and 6 µs (#204984).
  • A benchmark model with no weights. cm3leon_generate is built without initializing its weights: 2.6 GB of zeros in memory that was never written, which the kernel serves from one 4 KB page. Every compiler looked faster on it than a model with weights allows (eager 5.7 s; 9.9 s once the weights are written), and it made the one-row rewrite look like 0.43 where it is 0.68. The harness now writes every weight once (#205088).
  • Weights copied on every decoder step. A small region had built in 145 matrices it never used; the decoder-step graph read the same matrices through writable pointers, so each was copied on every step, and the measurement gave up on the compiled code. Only what a graph uses is built in now.
  • Too many workers for the container. Nine training processes at once went past the 256 GiB of the container the benchmark ran in, which killed it as a whole, four times, before the cause was understood. The harness now reads the cgroup limit, starts nothing above a fraction of it, and stops its own largest process above a second mark (#205096). The final run peaked at 161 GiB.
  • A leak, found by that guard. The first process the guard stopped was hf_Bart's training under torch.rewrite, at 55 GB where eager peaks at 8 GB. A region that is handed a loss module built inside forward, as every model of transformers does, made a variant per step, and each variant kept that step's logits alive: 393 MB per step. Fixed, with the price that the small region around such a loss now runs uncompiled (#205102, #205103).
  • A trace that used up a generator. A region that spans blocks is traced by running its instructions on copies of what it was handed; a generator cannot be copied, and where a region began with tuple(gen) the trace emptied it, so the call got (): a wrong result, once, without an error, since the third version. It surfaced in the sixth, when the frame hook brought ModelOutput.to_tuple of transformers into the VM and two models failed in a re-run on the CPU (#205272).
  • Handed back to the interpreter before it had a graph. The measurement that leaves slow code to the interpreter was taken while regions were still running their instructions one by one, so on the GPU, where the VM's own margin is small, whole transformer layers were left to the interpreter and never came back (section 9).
  • The VM's own call, caught by its own hook. To let the interpreter look at signals and other threads, the VM calls an empty Python function. With the frame hook that call came back to the VM, and other threads starved; one test caught it.
  • A CPU re-run under load. The sixth version was run again on the CPU while the GPU run shared the machine. Models bound by memory bandwidth took up to 1.8 times as long as in the fifth version's run; alone, they take what they took (dlrm 49.3 and 49.7 ms). The CPU numbers of this page are therefore still the fifth version's.
  • A memory table that mixed two measurements. Thirteen training rows of the last version's results were from a run made before the harness recorded the peak of the torch.rewrite process ahead of the calls in turns, so their peak included torch.compile and its copy of the model in the same process. They were left out of the geometric mean that was reported (1.07 over 35 models), but they stood in the table, and densenet121 looked like 68 GB against 33 GB there. Every row of this version is measured the same way.
  • A recording that kept a model's tensors alive. The 18 GB of hf_Reformer was attributed to the workspace for a day. It was the VM's recording of a C function's kernel calls (section 7), found only when the same peak showed with the workspace switched off.
  • Tests that passed without the feature. Small functions are inlined into the compiled function, so three new tests never exercised the code they were written for. Every new test is now run against the parent commit, and must fail there.

13. Suggested next steps

  1. Make the graphs before the first call runs. What is left of the memory cost is the first calls of a function, which run kernel by kernel and hold more at once than its graphs do later (section 7). Tracing a region on the arguments of the first call, instead of after a few calls that are surveyed, would take that away, and with it most of the time to the steady state.
  2. Run generators in the VM where it pays. With the variables in the frame, a generator's state can live where the interpreter keeps it. On its own the measurement would hand a generator back to the interpreter; it pays where the body is inlined into the loop that drives it. The hold instruction, which keeps a value alive as long as its variable, is redundant now that the frame does, and removing it takes values out of what regions are handed.
  3. Keep the loss region of transformer models compiled. Name a module that has no tensors by its class and attribute values instead of its identity, so that a loss built on every call is one variant and not one per call. The leak fix retires that region instead, which is safe and gives up a little speed on every HuggingFace training step.
  4. Modules with hooks, and branches on data. A region refuses a module with hooks, and with real convolutions that is the largest gap there is: opacus_cifar10 runs at the speed of eager where torch.compile gets 2.8 times. Lifting the refusal is not enough (tried): the results stay right, a hook that changes an output is traced, but a hook that appends to a list is run at the trace and never again. A branch on what a tensor holds still ends a region (hf_Bart checks every layer's output for infinities), and a loop over the layers of a ModuleList is not unrolled.
  5. Enter a region from a cold cache. The dicts of the modules tell of their changes now, and a call that is like the one before is told so in one pass in the runtime. What is left shows on calls of under a tenth of a millisecond right after an eager call of the same model, which is how the dashboard's runner times: a look at every tensor of the modules a region is handed, about 230 nanoseconds a tensor on memory that was pushed out of the cache. A region also cannot hold a with whose manager a functools.partial makes (the runner's autocast), so the VM runs it around the graph.
  6. Look for more kernels that do not use the machine. With memory and weights handled, what is left on the CPU is in the kernels: BLAS for transformers on batches, MKLDNN for convolutions. The one-row product was found by asking, per kernel, how many cores it used. A profile of every model in that form would find the others, if there are any.
  7. Close the guard gap. Trace callees through the VM's own graphs instead of running them in the interpreter during a trace, so that every read is seen and guarded. This is the main soundness difference from Dynamo.
  8. Compile what training still leaves to the interpreter, and decide sooner. Frames that C++ enters (a custom autograd.Function's forward, as in hf_Reformer), which the VM cannot see today. And the measurement of a function against the interpreter goes one level of calls after the other, about thirty calls a level: a training step, which goes through an optimizer, is still being measured after several hundred calls.
  9. Make the VM fast on Python, or keep handing it back: inline caches for attribute loads and method calls are the first candidates.
  10. Move the walk over a region's arguments into Rust. It is 0.4 ms per decoder step of T5 and the reason very short calls are behind.
  11. Review and land from the bottom. The five PRs with CI are the dispatcher hook; everything above depends on a decision about whether this front end is wanted. Several PRs above are larger than a reviewer should be asked to read.
  12. Report the cm3leon_generate finding upstream. A benchmark whose weights are unwritten zeros reads one page of the kernel over and over, for every compiler.
