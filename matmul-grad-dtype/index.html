Should matmul's backward honor grad_dtype?

An explanation of a design discussion: bf16 matmul inputs, an fp32 grad_dtype, and whether the native backward formula should output fp32 directly.

TL;DR. Today a bf16 mm backward rounds its result to bf16, and then the engine upcasts it to fp32 because of grad_dtype. The fp32 gradient therefore has only bf16 precision. The proposal is to have the formula output fp32 directly. The objection is about layering: grad_dtype is a cast instruction to the engine, not a hint for backward formulas, and no other op reads it. The counter-proposal is to make mm(..., out_dtype=fp32) differentiable, so the intent is stated explicitly in the forward instead of being inferred.

1. What grad_dtype is

Tensor.grad_dtype is a fairly new attribute that lets a leaf tensor's .grad have a different dtype from the tensor itself. The typical use is bf16 weights with fp32 gradients. From the docstring (torch/_tensor_docs.py):

By default, t.grad_dtype == t.dtype. When not None, the autograd engine casts
incoming gradients to this dtype.

That is the whole mechanism. The engine casts the gradient after the backward formula has produced it. Backward formulas don't read it.

2. What happens today

x = torch.randn(m, k, dtype=torch.bfloat16)
W = torch.randn(k, n, dtype=torch.bfloat16, requires_grad=True)
W.grad_dtype = torch.float32

y = x @ W
y.sum().backward()

1. mm backward formula

grad_W = x.T @ grad_y runs as a bf16 matmul. Tensor cores accumulate in fp32, but the output is rounded to bf16 when it's written.
→

2. engine cast

The engine sees grad_dtype = fp32 and upcasts the bf16 result. The precision lost in step 1 doesn't come back.

The result is an fp32 gradient with only bf16 precision, produced by a downcast followed by an upcast.

3. The proposal

When the backward formula can tell that the gradient will end up fp32, it should run the matmul with out_dtype=fp32 and skip the rounding. The cost is the same single matmul, because the accumulator was already fp32. The output is more precise. Changing the default numerics is mildly BC-breaking, but grad_dtype is new enough that few users depend on the current behavior, and the argument goes that defaults matter.

4. The objection

  • Layering. grad_dtype tells the engine what dtype to cast to. It was not designed as a signal backward formulas should read. If you want backward to compute in a particular precision, write a custom autograd.Function; that is the use case grad_dtype was added for.
  • Consistency. No other op's formula reads it. Making mm the exception invites the same change for bmm, addmm, linear, conv, and so on.
  • No mind reading. Core shouldn't guess what precision a user wants from a field that means something else.

5. The counter-proposal: differentiable mm with out_dtype

The mm.dtype overload already exists in native_functions.yaml:

- func: mm.dtype(Tensor self, Tensor mat2, ScalarType out_dtype) -> Tensor

It has no entry in derivatives.yaml, so it isn't differentiable today. The proposal is to add backward support for the bf16-to-fp32 case. With this, the user asks for fp32 explicitly in the forward, and nothing has to be inferred.

The hard part is that the incoming gradient grad_y is now fp32, so grad_W = x.T @ grad_y is an fp32 × bf16 product with no fast native kernel. The trick is to split the fp32 tensor into three bf16 pieces:

hi  = g.bfloat16()
mid = (g - hi.float()).bfloat16()
lo  = (g - hi.float() - mid.float()).bfloat16()
# g ~= hi + mid + lo   (3 x 8-bit mantissas ~ fp32's 24 bits)

grad_W = x.T @ hi + x.T @ mid + x.T @ lo   # 3 bf16 matmuls, fp32 accumulation

Because the other operand is exactly bf16, three bf16 matmuls recover close to fp32 accuracy. That is the "3 bf16 matmuls for each gradient".

Why bf16 and not fp16? bf16 has the same 8-bit exponent as fp32, so every piece of the split fits in range. fp16 has a 5-bit exponent, so the small residual pieces underflow or overflow, and the split breaks down.

Schemes that use more matmuls for still more precision (a "4 matmul" variant was mentioned) are out of scope for core and belong in a custom autograd.Function.

6. The follow-up question, and the answer

The follow-up points out that the original case is simpler than the one the counter-proposal handles. There, grad_y is still bf16, so no splitting or extra matmuls are needed. Changing the output dtype just removes a pointless downcast-then-upcast, at no cost.

That's correct, and it means the cost argument doesn't apply. What remains is the principle:

  • Layering is the real objection. Backward formulas would start depending on what dtype some downstream leaf wants.
  • It's fragile. If W passes through anything before the mm (a .to(), a view, an FSDP all-gather), the mm input is no longer the leaf with grad_dtype set. The optimization would then silently stop applying.
  • The gain is smaller than it sounds. The main benefit of an fp32 grad_dtype is accumulating across microbatches and reductions in fp32, and that still happens. What is skipped is one bf16 rounding per matmul, a relative error of about 2-9, applied once.
