A quarter of a training step, lost to one Python frame: the chunks of CPython's frame stack under a compiled graph

A training step of tf_efficientnet_b0 took 30.5 ms under torch.vm in the perf dashboard's runner and 23.3 ms in a probe of the same runner. The difference was where a 16 KB chunk of the interpreter's frame stack ends: how that was found, what it is, that torch.compile has it too, which CPython versions have it, and what was done. Nov 18, 2026.

In short. On the perf dashboard's training suites, torch.vm (a prototype compiler, written up here) was level with torch.compile in the mean, and on two timm models it took a quarter longer for a reason that could not be named: the same graphs, the same kernels on the GPU, as many of them. The reason is in neither compiler. CPython 3.11 and 3.12 keep the frames of a thread in chunks of 16 KB, and give a chunk back to the system the moment the frame at its start returns. The code Inductor generates for a graph is one function with one large frame, which launches the graph's kernels one after the other. Where the dashboard's runner calls that function for tf_efficientnet_b0 under torch.vm, its frame ends 128 bytes before the end of a chunk; a kernel launch needs 288 bytes for the first frame it calls, so each launch maps a new chunk and unmaps it again, 452 times in a step. One more Python frame anywhere above, and the generated function's frame no longer fits either and starts a chunk of its own, with room to spare.

It is an accident of the depth of the caller, to the byte. torch.compile has it on four other training models in the same runner. CPython fixed it in March 2026 for 3.13 and 3.14 (python/cpython#142183), not for 3.11 and 3.12, and the perf dashboard's jobs run 3.11. The prototype's runtime now keeps the chunks that the interpreter frees (#205502), and the suites were measured again with a count of the chunks every run asks for.

1. The symptom

The perf dashboard measures torch.compile with benchmarks/dynamo: a runner that loads a model, warms the compiled function up, and then times thirty compiled calls against thirty eager ones, in turns. #205357 lets that runner measure torch.vm the same way. For training (--training --amp) the two compilers came out level in the mean once the update of the optimizer was compiled too: 1.00 of the time of torch.compile on HuggingFace, 1.01 on timm, 0.97 on TorchBench. On timm, two models stood out:

model (batch 128)torch.compiletorch.vmtime of torch.vm over torch.compile
tf_efficientnet_b024.3 ms a step (2.22x eager)30.4 ms (1.78x)1.25
repvgg_a219.8 ms (2.17x)22.3 ms (1.91x)1.13

Both compilers hand the same forward and loss to Inductor as one graph, and AOTAutograd derives the same backward. A profile showed the same kernels on the GPU under both, as many launches a step, and 6.5 ms more of the CPU's time inside the call of the forward graph under torch.vm. The report of that day said so, and said "why was not found". And a probe that replaced the runner's timed loop with a copy of it, in the same process, on the same warmed-up function, measured 23.3 ms where the runner measured 30.5 ms.

2. The path

Each step is given with what it was meant to rule out and what it showed. Times are of one training step of tf_efficientnet_b0 under torch.vm unless said otherwise.

Not the GPU, not the run

The machine is shared, and an earlier set of numbers had been spoiled by other work on the GPU. So the pair was run three more times with nothing else on it: 24.5 to 24.6 ms under torch.compile, 29.9 to 30.5 ms under torch.vm, and every one of the thirty timed calls of a run within a millisecond of the others. The probe, run again: 23.3 to 23.8 ms, every call. Two stable numbers for one function.

The runner's own loop inside the probe

If the probe's copy of the timed loop differs from the runner's, running the runner's loop inside the probe should show it. It did the opposite: the probe's loop measured 30.2 ms, then the runner's own loop, called right after it in the same process, 23.7 ms, then the probe's loop again 30.1 ms. A wrapper was then put around the runner's timed function to log each call's time, and with it every loop measured 23.4 ms. A measurement that changes what it measures; but what a logging wrapper changes is only that there is one more Python function between the loop and the step.

A sampler, and two wrong ideas

py-spy was attached to the runner during a long timed loop, once as it is and once with the wrapper. With native stacks it could not unwind through the Rust VM that runs the rewritten function, and lost most samples of the compiled call. With Python stacks only, the two runs differ in one place: the samples whose innermost frame is a line of the generated function of the forward graph.

Every kind of line was slower by about half, which looked like the interpreter itself running slower there. Two ideas came from that, and both were wrong. The first: torch.vm installs a frame evaluation function (PEP 523) while a rewritten function runs, and takes it out around the call of a compiled graph; if it stayed in, every Python call under the graph would go through it. The code takes it out, and a convolution is a C function, which no evaluation function touches. The second: another Python thread holding the GIL. The samples have no such thread. What the table shows in hindsight: the time is at the lines of the generated function, which is where a sampler of Python frames sees the interpreter while it makes room for a callee's frame. But the lines that call a convolution or allocate an output call C functions, which make no frame, and they were slower too. Unmapping memory several hundred times a step has costs beyond the call that does it; that is as far as this was taken.

The same call from 140 depths

If one frame more makes the step fast, how many frames make it slow again? The step was called through a chain of small functions of growing length, each adding a frame of 120 bytes.

A period of 16 KB in the depth of the Python stack is the size of a chunk of CPython's frame stack. The window is four or five frames of 120 bytes wide: about 3% of all depths.

The frames, and a count

The interpreter's own frames were then read at the moment the forward graph launches its first kernel (a wrapper around CPython's arena allocator, installed without adding a frame to any stack, notes which function is running when a chunk is asked for, and how much the current chunk has left). Under torch.vm there are 23 frames from the script's module down to the generated function, 16,224 bytes, of which the generated function's frame is 11,176: it has 1,027 local variables and room for 361 values on its stack. The frames of a thread's first chunk start 32 bytes into it, so the chunk has 16,384 − 32 − 16,224 = 128 bytes left. The first frame a kernel launch calls (CachingAutotuner.run) is 288 bytes.

The count, over the thirty repetitions of the runner's timed loop: 13,560 chunks asked for, 452 in every repetition: 368 kernel launches, 81 calls of assert_tensor_metadata (a Python function the generated code calls after an extern kernel), and three others. With the allocator keeping the freed chunks and handing them back, and nothing else changed, the same runner measures 2.25x where it measured 1.77x. That closed it.

It also explains the probe that disagreed with itself: its loop and the runner's loop are two functions with frames of different sizes, and the difference put one of them inside the window and the other outside.

3. What the interpreter does

Since 3.11 CPython does not allocate a frame per call. A thread has a stack of frames made of chunks of 16 KB (DATA_STACK_CHUNK_SIZE); a call bumps a pointer, and a return bumps it back. When a frame does not fit in what is left of the current chunk, the interpreter asks its arena allocator for a new chunk (an mmap), puts the frame at its start, and links the chunk to the one before. When that frame returns, _PyThreadState_PopFrame sees that it was the first of its chunk and frees the chunk (a munmap). The next call from the same place does it all again: two system calls and a page fault where a call otherwise moves a pointer.

It takes no PyTorch to see it. tools/chunk_cliff.py calls a small function 2000 times from each of 200 depths of the stack and reads the page faults of the process around each:

The CPython developers know it as "Calls across stack chunks perform badly" (December 2025). The change that keeps one freed chunk per thread (gh-145789, "Cache one datachunk per tstate to prevent alloc/dealloc thrashing") was merged in March 2026 and backported to 3.14 and to 3.13 that month; the 3.13.15 and 3.14.7 on this machine have the field (datastack_cached_chunk) and no slow depth. 3.11 and 3.12 take security fixes only, and the newest of each, 3.11.16 and 3.12.14, have the cliff. The build these measurements were made on is CPython 3.12; the perf dashboard's jobs (inductor-perf-test-nightly-h100.yml) set python-version: "3.11".

Why a compiled graph is where it shows: the cliff needs a function that makes many calls and whose own frame ends just before a chunk's end. Ordinary functions have frames of a few hundred bytes and make a handful of calls each. The function Inductor generates for a graph has a frame of several kilobytes to tens of kilobytes (every buffer is a local variable) and makes one call per kernel, hundreds to thousands in a row.

4. Whom it hits

The count was then made for every run of the dashboard's suites, with the runner started as the dashboard starts it. Each model was run under the compilers one right after the other, on the build that keeps the freed chunks, so a chunk that torch.vm asks for is counted but costs nothing, and one that torch.compile asks for is mapped as it would be on the dashboard.

torch.compile does not have it on tf_efficientnet_b0 because Dynamo splits the runner's training step where the model is called, and the function that resumes after the split has a frame of 4,880 bytes: with it on the stack the generated function never fits in the first chunk, starts its own, and has 5 KB left for what it calls (second row of the figure above). On ElectraForCausalLM the generated function is smaller (7,368 bytes), fits, and ends 256 bytes before the end of the chunk: 255 kernel launches a step each map a chunk. Six of 150 training runs, none of 258 inference runs: which ones is decided by the sizes of two dozen frames, and would be other models from another script, another Python version, or one more decorator.

What the mapping costs was measured both ways: for torch.vm as the difference between the pairs before and after the runtime kept its chunks, for torch.compile by running its four models a second time with the same allocator wrapper keeping chunks in its process (which changes nothing else about torch.compile).

What a chunk costs a step is not a constant: from nothing measurable to 14 µs, where mapping and unmapping one takes 7 µs in a small single-threaded process. The low numbers have a likely reason that was not measured: a step that waits for the GPU anyway hides CPU time spent on chunks (nfnet_l0's convolutions are long), and a step of many short kernels does not. The 14 µs are twice what the small process pays; a process with a GPU context has more threads and a larger address space to unmap from, and that is only a guess.

5. What was done

  • The runtime keeps the chunks (#205502). CPython asks its arena allocator for chunks, and that allocator can be replaced through a public function (PyObject_SetArenaAllocator). When the first function is handed to torch.vm, the runtime puts a small allocator in front of it that answers a request for exactly 16 KB with a chunk it kept, keeps up to four chunks of that size when they are freed, and hands every other request through. At most 64 KB are held. A test counts the page faults of 2000 calls from each of 160 depths: 2000 at one depth without the change, 1 with it. Under CPython 3.13 and 3.14 the interpreter's own cache answers first and this is seldom asked for anything.
  • Not done: anything for torch.compile. The same wrapper would take the accident out of its runs on 3.11 and 3.12, and so could generated code that makes sure of some room before it starts launching. Neither is part of this stack. In these runs the accident made four of its 75 training models' steps longer by nothing to 12%.
  • The numbers were measured again, all of them, in pairs, with the count next to each (below).

Found on the way: a compile inside the timed loop

The same count showed thousands of chunks in inference runs of torch.vm, all of them in the first repetition of the timed loop and none after: a compile. The runner warms a function up with its default arguments and then times it with collect_outputs=False; that flag is an argument of the region torch.vm compiles, part of its key, though no graph uses it, so the first timed call compiled the same graph a second time. The medians of thirty repetitions were not affected, but the compile time the runner reported left that compile out. The warm-up for --vm now calls the function as the timed loop does (#205357), and its compile time is what the warm-up took beyond as many calls of the settled function. That an unused argument is in a key at all is a weakness of torch.vm, and is still there.

timm for training went from 1.011 to 0.997 with the two models back in line. HuggingFace for training did not move, because the accident there is torch.compile's: with its four models run again and their chunks kept, its step of ElectraForCausalLM is 12% shorter, HuggingFace goes from 1.002 to 1.008 and training as a whole from 0.988 to 0.990. Inference did not move at all.

A caution that the second set of pairs made possible: between the two runs of the training pairs, five hours apart, the ratio of a model moved by 1.3% at the median and by up to 11% for the 57 models whose step takes 8 ms or more, and by 5.5% and up to 26% for the 16 with shorter steps. Part of that is the machine and part is torch.vm itself, which decides by measurement which functions to leave to the interpreter and does not always decide the same. The means are steady; a single model's ratio is not, and a gap of a few percent on one model is not a finding until it has been seen twice.

8. What is not known

  • Whether the perf dashboard's own numbers carry this for some models. Its jobs run CPython 3.11, which has the cliff, and its runner is the one measured here; but frame sizes differ between 3.11 and 3.12, so the models would be other ones. Nothing was run on 3.11 with PyTorch.
  • Why a chunk costs a step 14 µs in one process and nothing measurable in another (section 4 has a guess).
  • The backward graphs run on the autograd engine's thread, which has a frame stack of its own. The count covers all threads, and nothing of size showed on that one in these suites; a model whose backward function ends near the end of that thread's first chunk would have it.
  • Other callers. Everything here is the dashboard's runner. A training loop of a user's has its own depth, and on CPython 3.11 or 3.12 about one position in thirty is a bad one for a given graph.

9. Reproducing

The folder of this page has the data (results/) and the tools (code/tools/, with a README): the plain-Python script, the depth scan, the allocator wrappers in C, and the sitecustomize.py that installs a wrapper at the start of the runner's timed loop without adding a frame. The shortest way to see the cliff is python3.12 code/tools/chunk_cliff.py. For a benchmark of one's own on CPython 3.11 or 3.12: count the chunks, or time it once more with a frame added above it.
