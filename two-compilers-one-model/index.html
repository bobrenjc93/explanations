One model, two compilers, the same agent for three hours each

Where torch.compile and torch.vm start on one model, and how fast each climbs when the same AI agent is given three hours to improve it: throughput against the time and tokens spent, with the predictions and training curves checked against eager. Nov 19, 2026.

torch.vm is a prototype compiler for PyTorch: it runs a function's bytecode as a control-flow graph in a small VM and hands the tensor work to the same backend torch.compile uses (AOTAutograd and Inductor). On the performance dashboard's suites torch.vm is a little ahead on average, and a few models are far behind. This page takes the one where torch.vm was furthest behind, TorchBench's yolov3 in inference (1.00x of eager against 2.50x), and asks a different question: not where the two compilers are today, but what an hour of work buys in each. Two instances of the same AI coding agent (Claude) got the same instructions and three hours, one for each compiler: its options and its source were theirs to change, the model and the measurement were not. Every gain was recorded by a harness neither could touch. The chart is those records against what the agent had spent by then.

In short. torch.compile started higher (2,013 images/s against 784; eager does 802) and torch.vm climbed faster: after three hours of one agent each, 3,973 against 4,507. By time, torch.vm is ahead from 105 minutes on. By tokens, torch.compile is ahead at every budget up to the $30 its agent spent; the torch.vm agent spent $41 in the same three hours and passed it at $32. Two things qualify the end points. The top of the torch.compile line is reached with freezing and an unsafe guard filter, after which it no longer follows a weight update or model.train(); the fastest torch.compile state measured that passes every probe does 2,781. And the last 1,250 images/s of torch.vm come from a fused cuDNN kernel its agent wrote as a pass, which is a kernel either compiler could call; without it the line ends at 3,261. Every recorded state of both sides predicts as well as eager on real weights and images.

What the chart shows

  • Start. torch.compile gets 2.5x of eager out of the box. torch.vm got nothing: the model assigns two buffers on every call, a region refused a store into a module's buffer, and so the model ran kernel by kernel. That one fix, 12 minutes in, is the largest step on the chart (784 to 1,983).
  • The first hour: the same ceiling from two sides. Both agents found the same thing in their first profile: 2.5 ms of GPU kernels inside 3.9 ms of wall time. Both turned to CUDA graphs (an option for torch.compile; the torch.vm agent built it, as a new option of Graphs). Both ended with the weights built into the graph: freezing for torch.compile, after a fix in Dynamo that this model needed; torch.vm does it by default, and its agent moved the checks that guard it behind the kernel launch. Both rewrote the max pools. At 70 minutes they were at 3,270 and 3,261, and torch.vm's agent measured the GPU busy for 97% of a call. They hand the same graph to the same backend, so they met at its kernels.
  • After that it is about kernels. torch.compile's agent changed Inductor's lowering (separable max pool, a zero channel for the first convolution) and turned on autotuning and the older, cheaper CUDA-graph path: 3,973. torch.vm's agent stopped at 86 minutes, saying what was left was below the noise; told to go on, it replaced convolution + batch norm + LeakyReLU with one cuDNN kernel through cuDNN's backend API, timed cuDNN's engine choices per layer, and reached 4,507. torch.compile's agent named the same fusion as its next step and did not build it.
  • Per token. The two agents read about the same amount (71 and 75 million cached input tokens); the torch.vm one wrote more (364k output tokens against 258k, most of the difference being the 600-line pass). At equal dollars torch.compile stays ahead through its whole budget.
  • Hollow dots. From 21 minutes on, every torch.compile measurement uses freezing, and from 59 minutes the guard filter skip_guard_on_all_nn_modules_unsafe. Its agent said so in every note. The only torch.compile measurements that still follow a weight update are the first two (2,013 and 2,641) and the ones taken afterwards with its final source (the square: 2,781). Every torch.vm measurement kept the weights watched; the final state is checked below.

Time and dollars are the agent's own at the moment of the measurement; the dollars are its tokens at Anthropic's list price for the model ($8 per million input, $40 output, $10 cache write, $0.20 cache read; what a cloud provider charges may differ). About 57 of each side's 183 minutes were spent waiting for the other side's GPU jobs.

What this does and does not show

  • One model, one run per side. It is an example of the two slopes, not a measurement of them. The model was picked because it is where torch.vm was furthest behind, which is where a steep climb is most likely.
  • Most of the climb is catching up. Of torch.vm's 3,723 images/s, 2,477 were reaching the ceiling torch.compile was already near. The rest is the fused kernel.
  • The agent knew one compiler and not the other. It has read torch.compile's source in training and had never seen torch.vm; it was given the documentation and the tree. The one-line diagnosis of this model in torch.vm's report was taken out of what it was given, and turned out to be wrong anyway (the report blamed the layer loop; the agent found the buffer stores).
  • What is not on the x axis: the tokens that built torch.vm up to today, and those of the session that set the experiment up and checked it (the harness, the checks on this page).
  • The rules allowed what each side did. Options that give up eager's behaviour were allowed if said; so was a kernel called from a pass. A stricter reading strikes both, and leaves 2,781 against 3,261: 17% apart, which is weights built into the graph while they are still watched.

How it was run

  • Model and setup as the PyTorch performance dashboard has them: eval mode, batches of 8 images of 3x384x512, bfloat16, no_grad, one H100. Each side starts from the dashboard's configuration.
  • Each agent may change its compiler's options and Python source (and Rust, for torch.vm), in its own copy of the tree; not the model, not the harness, not eager, no C++ build. Neither may use the other's compiler.
  • A measurement: the state is snapshotted, three processes each warm the callable up (at least 300 calls and 20 s) and time 400 calls on four different inputs; the median counts if the outputs match eager's by the dashboard's rule for bfloat16 and the probes pass (a weight updated in place, another batch size, the timed shape again).
  • Tokens are read from each agent's transcript, by the timestamp of each response.
  • Both agents stopped once before the deadline and were sent the same message to go on (torch.vm at 86 minutes, torch.compile at 152).
  • Found while the harness was built: the dashboard's runner compiles a function that calls the model, and that is what the torch.compile side starts from. torch.compile(model) on the module itself runs this model at 7.6 ms per batch instead of 4.0, with the same graphs. The cause was not looked into.

Appendix: every step, in detail

What each agent found, what it changed and why that is faster, in the order of the tables above. The figures inside a step (microseconds per kernel, milliseconds per call) are from the agent's own profiles, as its journal has them; the images/s in a heading are the recorded measurements before and after.

The model, for orientation. One call is a batch of 8 images through 76 convolutions. 73 of them are followed by a batch norm and a LeakyReLU, 23 results are added to an earlier one (the residual connections), one tensor goes through three max pools with windows of 5, 9 and 13, and three detection heads turn their convolution's output into boxes with a few sigmoids and exponentials; their three results are concatenated. Compiled, that is about 200 GPU kernels: the convolutions are cuDNN's, everything between them is kernels that Inductor generates, and they take about 2.5 ms together.

Three terms that come back.

  • Host time. Each kernel is launched from the CPU, through Python, PyTorch and the driver, at 10 to 25 microseconds apiece. For 200 small kernels that is more than the GPU needs to run them, so the GPU waits for the CPU.
  • CUDA graph. A recording of all the kernel launches of one call. Replaying it starts them with one call into the driver. The recording is tied to the memory the recorded call used, so each call's input is copied into it and each new shape needs a new recording.
  • Weights built in. A compiler can treat the model's weights as inputs of the graph (any tensor may show up there next call) or as constants of it. As constants they can be combined ahead of time: an inference-mode batch norm is a multiply and an add per channel, and folds into the convolution's weights and bias, so the batch norm's arithmetic leaves the call. The price is that the graph is only right while the weights are what they were. torch.compile calls this freezing and does not notice a weight that is updated in place afterwards; torch.vm does it by default and watches the weights.

torch.compile

Start: the dashboard's configuration

2,013 images/s, 3.98 ms per batch. The agent's first profile: a call takes 3.90 ms, the CPU is busy launching kernels for 3.83 ms of it, and the kernels themselves add up to 2.54 ms (the 76 cuDNN convolutions are 61% of that). The host is the bottleneck, not the GPU.

1. CUDA graphs 2,013 → 2,641 images/s

Change. One option: mode="reduce-overhead", later written as options={"triton.cudagraphs": True}. Inductor records the compiled graph's kernels as a CUDA graph and replays it.

Why it helps. The 200 launches become one. A call goes from 3.9 ms to 3.0 ms, not far from what the kernels themselves take.

Cost. The memory of the recorded call stays allocated. Nothing eager does is given up: this state follows every probe.

2. Freezing, and the fix in Dynamo it needed 2,641 → 2,909 images/s

Change. torch._inductor.config.freezing = True builds the weights into the graph: the 73 batch norms fold into their convolutions, and the weights are converted to cuDNN's preferred memory layout (channels last) once, at compile time, instead of being handed over in the other layout on every call.

Why it did not work at first. With freezing on, the model fell back to eager (748 images/s): Dynamo recompiled on every call until it hit its limit. Each of the model's three YOLO layers rebuilds a small grid tensor on every call and assigns it to a buffer:

def forward(self, p, out):
    bs, _, ny, nx = p.shape
    self.grid = self.create_grids((nx, ny), p.device)   # a registered buffer, replaced on every call

Freezing guards the identity of every tensor it builds in, so that a different tensor in its place triggers a recompilation. Assigning to a buffer goes through nn.Module.__setattr__, which first looks the name up; in Dynamo that lookup took the old buffer's value far enough to install its identity guard, although the code never reads the old buffer, it only overwrites it. The guard then failed on every call, because the buffer is a new tensor every time.

The fix is 11 lines in torch/_dynamo/variables/user_defined.py: when that lookup finds a value that has not been used yet and is not a submodule, leave it unused, so no guard is installed for it. On a small reproduction that is one graph where there were six.

What it gives up. The compiled code computes with the weights as they were at compile time. The probes confirm it: an in-place update of a convolution's weight, a batch norm's bias or running mean is not followed.

3. Max pool one dimension at a time, in Inductor 2,909 → 3,051 images/s

What the profile said. The three max pools took 19, 26 and 99 microseconds: 145 of the 2,430 the kernels take. Inductor computes each output as the maximum over the whole window, so the 13-window reads 169 values for every output element.

Change, in torch/_inductor/lowering.py: the maximum over a rectangle is the maximum over its rows of the maximum along each row. So when only the pooled values are used (not the positions of the maxima), the pool is computed one dimension at a time: 13 values along one dimension, written to memory, then 13 along the other. That is 26 reads and one extra write per element instead of 169. It applies only where it at least halves the reads, and the path that also returns indices is unchanged.

Second change, a setting. Inductor can compute a torch.cat in two ways: as a kernel of its own into which each part is written (a "concat kernel"), or fused into one kernel with the arithmetic of its parts, where every output element first works out which part it belongs to. The fused form was the slowest kernel that is not a convolution, for the model's final concatenation of the three heads. max_pointwise_cat_inputs = 1 makes every concatenation a kernel of its own. (Step 6 refines this.)

4. Guard filter (unsafe) 3,051 → 3,270 images/s

What the profile said. Of the 0.32 ms the CPU still spends per call, launching the CUDA graph is 58 microseconds and copying the input 17. The rest, about 250, is Dynamo's guards and the Python around them. Before it runs compiled code, Dynamo checks that everything the code assumed still holds; for this model that is about 4,700 checks on the attributes of its 225 modules (is this module still in eval mode, is this still the same parameter, are there still no hooks).

Change. torch.compile(..., options={"guard_filter_fn": torch.compiler.skip_guard_on_all_nn_modules_unsafe}) drops the guards on module attributes. The guard check goes from 149 microseconds to 3.

What it gives up, as the name says: a change to a module after compilation is not noticed. In the probes, model.train() and a replaced parameter are not followed. The agent tried two sound alternatives first (use_recursive_dict_tags_for_guards: 149 to 126 microseconds; skipping only the guards of PyTorch's built-in modules: 59 microseconds, 3,180 images/s) and recorded two reference rows without the filter at the end: it is worth about 8%.

5. Pool stages as unrolled kernels 3,270 → 3,328 images/s

The two stages of the 9- and 13-wide pools from step 3 were generated as reduction kernels: a loop with a running maximum for each output element, 16 microseconds each. For a window this short, a kernel that simply reads the 9 or 13 values and takes their maximum in one expression is faster. Inductor already does that below a threshold (unroll_reductions_threshold, 8 by default); the lowering now raises it to 26 for these stages.

6. Concatenation and in-place settings 3,328 → 3,420 images/s

Two settings. max_pointwise_cat_inputs = 2: concatenations of two parts are fused with their parts again (the model has small ones where that is cheaper), those of three or four stay kernels of their own. inplace_buffers = False: by default a generated kernel may write its result over its input when nothing else needs the input, which is what the bias-and-LeakyReLU kernel after each convolution did. Writing to a fresh buffer measured faster here: the largest such kernel (the first layer's, 100 MB) took 65 microseconds instead of 91. The agent measured this and did not find out why.

7. A fourth input channel for the first convolution 3,420 → 3,453 images/s

What was measured. The first convolution reads images with 3 channels, and cuDNN's half-precision kernels are slow for exactly that: 101 microseconds, against 74 when the input has a fourth channel of zeros (8 channels: no further gain; 16: slower).

Change, in torch/_inductor/kernel/conv.py: a half-precision, channels-last convolution with 3 input channels gets a zero channel appended to its input and zero weights for it. A zero times a zero adds exactly nothing to any sum; what changes is which kernel cuDNN picks, and the agent's checks agree with eager to within one unit in the last place. The input is padded in the kernel that already converts it to channels last, and a built-in weight is padded once at compile time.

8. A smaller inlining threshold 3,453 → 3,467 images/s

Inductor keeps an expression inside the kernels that use it until it has more than 30 operations, and only then computes it into memory of its own. Each detection head ends with four assignments to slices of one tensor:

io[..., :2] = torch.sigmoid(io[..., :2]) + self.grid
io[..., 2:4] = torch.exp(io[..., 2:4]) * self.anchor_wh
io[..., :4] *= self.stride
torch.sigmoid_(io[..., 4:])

Each one wraps the expression before it in a condition ("if this element is in the slice, the new value, else the old one"), so the inlined expression doubles four times, and an element can evaluate a sigmoid or an exponential several times. realize_opcount_threshold = 20 cuts the chain earlier. The gain is within the noise of the measurement.

9. Autotune: Inductor's own kernels for the 1x1 convolutions 3,467 → 3,806 images/s

Change. torch._inductor.config.max_autotune = True. For every convolution and matrix product, Inductor generates candidates (its own Triton kernels in several tile sizes, next to cuDNN's and cuBLAS's), times them while compiling, and keeps the fastest. Compiling takes about 50 s longer.

What it picked. A 1x1 convolution is a matrix product. For 36 of the model's 38 such convolutions Inductor's own kernel won, and that kernel adds the bias and applies the LeakyReLU before it writes its result, so the separate pass over the output afterwards is gone. The 38 3x3 convolutions stayed with cuDNN, which still needs that second pass. Per call afterwards: cuDNN's 3x3 convolutions 1,143 microseconds, the 36 generated kernels 317, the bias-and-LeakyReLU passes after cuDNN 383.

Only with freezing. The agent had tried the same option at the start, with the weights as inputs, and it gave nothing (2,659 against 2,653).

10. CUDA graphs without the tree bookkeeping 3,816 → 3,973 images/s

Inductor's default CUDA-graph support keeps a tree of recordings that share one pool of memory, tracks which results of earlier calls are still alive, and raises an error when a program touches a result that a later call has overwritten. That costs about 40 microseconds per call. "triton.cudagraph_trees": False selects the older path with one recording per graph: the CPU's share of a call goes from 0.160 to 0.125 ms.

What it gives up. Results are fixed buffers that the next call overwrites without a word. A program that keeps a result across calls reads the wrong numbers instead of getting an error.

The rows that are not steps

Hardening (3,446): the agent reviewed its convolution change and added a case it had missed (a built-in weight that lives on another device than it is used on is padded at run time). No change in speed was expected. Reference rows (3,539 and 3,664): the two best configurations measured again without the guard filter, so that the result has points that do not depend on it. Repeats (3,816 and 3,887): the same state measured again. The last rows differ by up to 8% between processes; the agent traced that to cuDNN timing each convolution algorithm once per process and sometimes picking a slower one, and did not fix it.

Tried without gain: kernel autotuning before freezing; coordinate-descent tuning of the generated kernels; 1x1 convolutions as matrix products without autotune; padding the first convolution to 8 or 16 channels; other inlining thresholds; realizing the detection head's chain inside the lowering (the head's kernels got faster, the total did not).

torch.vm

Start: the dashboard's configuration

784 images/s: eager's speed, after 130 s of warm-up. torch.vm hands stretches of tensor code ("regions") to Inductor as graphs. torch.vm.regions(fn) showed that the region around the whole model had been refused, with the reason "__setattr__ on a module the region was given": the three YOLO layers assign a grid and a size to buffers of theirs on every call (the code under step 2 of torch.compile), and a region allowed such a store into a plain attribute but not into a registered buffer. Without the outer region the model fell apart into a region per layer, 73 graphs of a handful of operations, only 8 of them with weights built in. The VM then measured those against the interpreter, found them no faster, and handed the model's loop back to the interpreter.

1. Stores into module buffers allowed: one graph 784 → 1,983 images/s

Change, in torch/vm/_regions.py: a region may store a tensor it has computed into an existing buffer of a module, the way it already could into a plain attribute. The graph returns the tensor, and the region does the store after the graph has run, so the module ends up holding what eager would have left there.

Effect. The whole model is one region: one Inductor graph of 645 operations with the weights built in, compiled in 20 s. That is where torch.compile started (2,013).

2. CUDA graphs, built as a new option 1,983 → 2,456 images/s

What the profile said. The same as on the other side: a call returns after 3.9 ms while its kernels need 2.4. torch.vm had no CUDA-graph support, so the agent wrote it: Graphs("inductor", cuda_graphs=True).

How it works. The compiled code runs the first call. The second call is recorded as a CUDA graph and replayed once, and the recording is kept only if the replay gives the code's result bit for bit, writes to no input, and returns nothing that shares memory with an input or another result. Otherwise the compiled code goes on running. Each call's input is copied into the recording and each result is copied out, so a caller gets tensors of its own, as from eager.

When it does not apply. The graph must run on one GPU, with sizes that are all known, without operations whose work depends on a tensor's contents and without random numbers; and the code runs instead of the recording when gradients are being recorded, under a torch function or dispatch mode, while the caller is recording a CUDA graph of its own, or while another thread is replaying. The option is off by default; its cost is the recorded call's GPU memory.

3. The fast path kept after the region's own stores 2,456 → 2,863 images/s

Background. Before a region runs its graph, it has to establish that this call is like the one the graph was made for: the same modules, holding tensors of the same shapes and types, the same settings. Doing that from scratch takes about 0.6 ms of Python for this model. There is a fast path: if nothing in the modules has changed since the previous call, which the runtime can tell in one pass (about 40 microseconds), the previous answer stands.

The problem. This region changes the modules itself: it stores a new grid in the YOLO layers on every call (step 1). So every call found the modules changed and took the 0.6 ms path, before any kernel started.

Change. After a call that stored tensors into modules, the region establishes the answer again right away, for the modules as they now are. On a GPU that is after the kernels have been launched and while they run, so the 0.6 ms no longer delays anything; the next call finds the modules as that look left them and takes the fast path.

4. The weights check moved behind the kernel launch 2,863 → 3,108 images/s

Background. Because torch.vm builds the weights into the graph, it has to make sure on every call that none of the 290 built-in tensors has been written to or replaced since; that is what lets it follow a weight update where freezing does not. For the same reason as in step 3 this check ran the slow way on every call: 0.20 of the 0.27 ms that passed before the kernels were launched.

Change. The check for the next call is done behind the launch too, while the GPU is busy, and the next call only has to confirm that nothing was touched in between, which the fast path of step 3 already tells it. The time before the launch goes from 0.27 to 0.07 ms.

Is it still safe? This is the step that could have cost correctness: a weight written between two calls must still be noticed. The probes were run on this checkpoint for that reason, and every one is followed.

5. Pass: max pools of 5, 9 and 13 as a cascade of 5s 3,108 → 3,205 images/s

What a pass is. A function in the user's configuration that torch.vm calls with the graph of a region before the graph goes to Inductor. This one is 50 lines.

The rewrite. The model pools one tensor three times, with windows of 5, 9 and 13, all at stride 1. At stride 1, the maximum over a window of 9 is the maximum over a window of 5 of the maxima over windows of 5 (5 + 5 - 1 = 9), and 13 is one more round. So the pass computes the 5-pool, feeds its result to another 5-pool to get the 9, and that to a third to get the 13:

p5  = max_pool(x,  5)        # was: p5  = max_pool(x, 5)
p9  = max_pool(p5, 5)        #      p9  = max_pool(x, 9)     81 values per output
p13 = max_pool(p9, 5)        #      p13 = max_pool(x, 13)   169 values per output

A maximum involves no rounding, so the results are the same bits. The three pools had taken 145 microseconds. (torch.compile's agent attacked the same 145 microseconds inside Inductor, step 3 there.)

6. Pass: convolution, batch norm and LeakyReLU as one cuDNN kernel 3,261 → 3,476 images/s

What the profile said. A call was now 2.41 ms of kernels and under 0.2 ms of everything else. 62% of the kernel time is cuDNN's convolutions, and 26% is the kernel after each one that adds the bias and applies the LeakyReLU. That second kernel does almost no arithmetic: its time is reading the convolution's whole result from memory and writing it back.

The idea. If the convolution applied the bias and the activation before writing its result, the second pass over memory would not exist. The cuDNN interface that PyTorch calls can fuse a ReLU into a convolution but not a LeakyReLU. cuDNN also has a newer interface (its "backend" or graph API) that takes a small graph of operations (convolution, add a bias, a ReLU with a slope for negative values, add another tensor) and builds one kernel for it at run time. PyTorch does not expose it.

Change, all in the configuration file, about 500 lines. The agent called that interface with ctypes on the cuDNN library PyTorch has already loaded (no build), wrapped it as a custom operator y = leaky_relu(conv(x, w) + b) [+ z], and wrote a pass that replaces convolution → batch norm → LeakyReLU [→ add the residual] in the region's graph by that operator. The batch norm is folded into the weights and bias in float32.

Per layer, by measurement. The fused kernel is not always faster: one stride-2 layer took 270 microseconds fused against 63 + 32 apart. So the pass times both ways for each kind of layer when it compiles, and fuses only where that wins. 72 layers were fused at this step; the first layer, close to a tie, was not. Graphs with sizes that are not known are left as they were.

7. The first layer and the detection heads fused too 3,476 → 3,743 images/s

Three refinements of the pass. A layer left unfused between fused ones has its tensors copied between two memory layouts, so the pass now fuses unless the fused kernel is more than 10% slower; that brings in the first layer (104 + 68 microseconds plus an 81-microsecond layout copy before; 166 after). The three detection-head convolutions, which have a bias but no batch norm or activation, are fused with a slope of 1, which makes the LeakyReLU do nothing. And those heads have 255 output channels, where cuDNN's fastest kernels want a multiple of 8: the pass adds one all-zero filter to make 256 and cuts the extra channel off afterwards. The largest head went from 61 to 13 microseconds.

8. The fastest of cuDNN's first five kernel variants per layer 3,743 → 3,968 images/s

Background. For each small graph it is given, cuDNN has several implementations, which it calls engines, each with settings of its own. Asked for one, it returns a list of up to ten candidates ordered by a heuristic: its guess of the fastest first, without timing anything.

What was measured. The guess is often wrong. For a 3x3 convolution from 128 to 256 channels with the residual add, the first candidate took 35.4 microseconds and the second 31.3; for one from 64 to 128 channels, 61.3 against 42.9 for the third; for a 1x1, 9.7 against 8.2 for the fifth.

Change. When the pass sets a layer up, it runs the first five candidates on tensors of that layer's shapes and keeps the fastest. This is what torch.backends.cudnn.benchmark = True does for the interface PyTorch calls. The kernels of a call went from 2.02 to 1.88 ms.

9. Pass: the final concatenation as a kernel of its own 3,968 → 4,156 images/s

The model's result is the concatenation of the three heads' outputs. Inductor had fused it with the heads' arithmetic into one kernel, in which every element of the result evaluates the expressions of all three heads under conditions (the chain of slice assignments shown under step 8 of torch.compile): 126 reads, 39 sigmoids and 18 exponentials per element, 131 microseconds. The pass replaces a concatenation that is a result of the graph with an operator Inductor cannot fuse through, so each head is computed for its own elements only and the concatenation is a copy: 61 microseconds. (torch.compile's agent got the same effect with a setting, steps 3 and 6 there.)

10. Pass: each pool as two one-dimensional pools 4,156 → 4,253 images/s

On top of the cascade of step 5, each 5x5 pool is split into a 5x1 pool followed by a 1x5 pool: 10 values per output instead of 25, exact for the same reason. This is the rewrite torch.compile's agent put into Inductor's lowering.

11. Input channels padded to a multiple of 4 4,253 → 4,372 images/s

The same finding as torch.compile's step 7, for the fused kernel: with the image's 3 channels padded by a channel of zeros, the first layer takes 116 microseconds instead of 165. The pass pads the input channels of a fused convolution to a multiple of 4, with zero weights for the added ones.

12. The fastest of all ten kernel variants per layer 4,372 → 4,451 images/s

Step 8 timed the first five of cuDNN's candidates. For the 3x3 convolutions from 128 to 256 channels, of which the model has eight, the tenth turned out fastest: 25.9 microseconds against 31.3 for the best of the first five. The pass now times all ten. Compiling takes 37 s instead of 17.

The agent then tried the tuning settings inside the winning engine as well (56 values of one, a range of two others): none beat what the best of the ten already had.

13. The input read in place instead of copied 4,451 → 4,505 images/s

Replaying a CUDA graph meant copying each call's input into the memory the recording reads from: 30 microseconds. A caller that hands over the same memory again and again (one buffer it refills, a few it rotates through) now gets, at the third sighting of an address, a second recording made on its own tensor, which reads the input where it is. That recording is only made once the first one has shown that the code writes to no input and returns no memory of one, and it is checked by a bit-for-bit replay like the first. This is a change to the compiler, not the configuration.

The rows that are not steps

Hardening and documentation (3,165, 3,261, 3,234): the CUDA-graph option refuses graphs that draw random numbers (recording and then replaying to check would advance the generator twice) and steps aside when the caller is recording a CUDA graph itself; the look-ahead of step 4 was restricted to the part of the check that changes nothing; docstrings. These three rows have the same configuration, and show the noise: up to 1.5% from one measurement to the next, 0.3% between the three processes of one. Steadier timing (4,507): the timings that pick a kernel variant were lengthened, to see whether the remaining spread came from different picks. It did not.

Where a call's time is at the end. 1.77 ms. The kernels start about 60 microseconds after the call (40 of them the fast-path look over the modules' 370 tensors) and run for 1.7 ms, 91% of it in the fused cuDNN kernels; meanwhile the CPU copies the results out (90 microseconds) and prepares the next call (step 3, about 1 ms, hidden behind the GPU here; for a model with a shorter graph it would not be).

Tried without gain: coordinate-descent tuning of the generated kernels; convolutions in the other memory layout (3.64 ms against 2.53); 1x1 convolutions as matrix products; splitting the batch in two halves replayed on two streams at once (2.50 ms against 2.45).
